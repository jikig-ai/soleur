# P1b baseline — operands that are neither provably absolute nor guarded (#7708).
#
# SHRINK-ONLY. A row may fall; a row may not rise, and a new path may not appear. Regenerate with
#   bash plugins/soleur/test/fixture-relative-assert.test.sh --write-baseline
# and only in the same commit as the source edits that earned the shrink.
#
# WHAT THIS IS NOT. These are NOT 909 defects. P1b asks whether an operand can be RELATIVE, or be
# rooted at `/` by an empty parent. It does not assert any of these is reachable with such a value
# today. The rows are the residue left AFTER the scanner resolved everything it could: mktemp in
# every form, one-line and multi-line same-file wrappers, wrappers reached through a sourced helper
# (118 of the corpus's 232 source directives resolve), and bindings that sit on the SAME LINE as
# the use. What remains is dominated by roots the scanner cannot see through — `never-bound`
# globals, positional parameters supplied by a caller, and uses that textually PRECEDE their
# binding (a helper defined above the assignment it reads).
#
# WHY GRANDFATHERED RATHER THAN BURNED DOWN, measured against the repo fix-inline threshold of
# 100 lines / 4 files:
#
#   family      sites  files   disposition
#   git -C          0      0   REMEDIATED INLINE in #7708 (was 17 across 3) -- no git-C row below
#   rm -rf        194     40   grandfathered
#   redirect      695    171   grandfathered
#   mv / cp -r     20     18   grandfathered
#
# The three grandfathered families are an order of magnitude past the threshold. Filing the
# measured number beats asserting a fix. Burn-down is tracked on its own issue.
#
# `assert_fixture_dir` is a sound P1b guard, not merely a P1a one: its `case` rejects the empty
# string, `..` components, synthetic-fs paths and the filesystem root, accepts `/*`, and refuses
# everything else as RELATIVE. Clearing a relativity finding with it is therefore legitimate. A
# guard that only rejected EMPTY would not be, and must not be added to this rule recognised set.
#
# THE DANGEROUS DIRECTION, and this file has moved BOTH ways. Two resolver bugs made sites look
# SAFE: a one-line function body was never read (`range(hi, lo, -1)` is empty when hi == lo -- the
# same hazard as the one-line FUNC_HEAD finding in #7709), and `mktemp -d "$ROOT/c.XXXXXX"` was
# classified absolute when a path-bearing template inherits its prefix exactly as `-p` does.
# Fixing those moved the count UP, 982 -> 1114. Then teaching the resolver to read a same-line
# binding moved it DOWN, 1089 -> 909, because `L="$T/log"; : > "$L"` had been reported never-bound
# while `T` was plainly mktemp-rooted. That 180-row shrink was validated by reading the cleared
# sites, not by trusting the delta: in `tests/scripts/test-zot-log-channel-probe.sh` (28 -> 2) the
# cleared rows resolve through `TMP="$(mktemp -d)" || { ...; exit 2; }`, and the two survivors are
# uses that sit ABOVE that binding.
#
# A future change that shrinks this file deserves the same treatment. From the count alone, a
# better resolver and a detector that stopped looking are indistinguishable.
#
# mktemp absoluteness is ENVIRONMENTAL, not lexical: `TMPDIR=reldir mktemp -d` returns
# `reldir/tmp.XXXX`, measured on uutils coreutils 0.8.0. It is treated as absolute here because
# this corpus has zero relative TMPDIR literals and zero relative -p arguments -- established with
# a positive control proving the pattern can match -- not because mktemp guarantees it.
#
# Excluded by NAME as CI plumbing rather than fixture dirs: $GITHUB_OUTPUT, $GITHUB_STEP_SUMMARY,
# $GITHUB_ENV, $GITHUB_PATH. Their shape is identical to a fixture write and no chain analysis
# separates them; flagging them is how a guard stops being read.
