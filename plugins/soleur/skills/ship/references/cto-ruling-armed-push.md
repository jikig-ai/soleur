# CTO ruling: an operator's "ask before pushing to an armed or queued PR" instruction

Loaded from `soleur:ship` Phase 7, in the required-check-failure path, when the operator's brief says to ask before pushing to an armed or queued PR and the fix is a push.

Before spawning the CTO: if the fix touches production code, workflow semantics, required-check configuration or the PR's scope, or involves a production write, an irreversible action or a legal-risk call, disarm auto-merge and return to the operator; do not ask the CTO. Otherwise (a test or harness defect, a lint or ratchet repin) the instruction is cleared by a `soleur:engineering:cto` ruling, not by asking the operator (`hr-technical-fork-is-not-an-operator-question`): brief it with the failing job and log tail, the `git diff --stat` of the unpushed commit, the local evidence and what is NOT proven, and record the answer as "Ruled by CTO agent". Ask for push armed or disarm first (default disarm, unless the ruling records that an armed push is safe), a pre-push condition, and a push bound. The bound is the ruling's number, never more than 3 pushes in all including the step-4 push; `fix_attempt_count` still increments on every push, and the same failure signature twice means disarm and return to the operator (precedent, PR #10294). Step 4a's re-queue applies only when the ruling says armed push; after a disarm, re-arm once the post-push log check below passes. **Headless mode:** the ruling's bound replaces the step-3 abort; on the bound, or on any disarm-and-return condition, abort with the structured error naming the failing check. After the push, read the re-run job log and confirm the step that failed actually ran: a green check from a skipped tier is not validation.
