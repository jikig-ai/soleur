# Queue mode (#9710)

The Queue mode paragraph below was moved verbatim out of `ship/SKILL.md` Phase 7 to stay under the SKILL.md body ceiling (ADR-229); the SKILL.md paragraph keeps the operative `queue_wait` rule. The Standalone guard paragraph (2026-10-09) was written here.

**Queue mode (#9710).** When `main` has a `merge_queue` rule (read once at loop entry by `.type == "merge_queue"`, never by position; this reads `main`'s rules, as the required-check read already does) and the required-check set is non-empty, AND auto-merge is armed (read each BEHIND tick), a BEHIND reading that GitHub itself reported is not a reason to push: each push restarts the whole required-check set, and the queue builds every candidate against the projected `main`, so an armed PR is made current by the queue. GitHub enqueues an armed PR whose head is behind `main` on its own (measured, ADR-270 canary addendum 2026-10-07), so the poll prints `[ship.phase7.queue_wait]` once and keeps polling (informational: take no action, and never sync, update-branch or merge it by hand until `[ship.phase7.queue_wait_expired]`, a push line, MERGED, a dequeue or any poll exit), prints `[ship.phase7.queued]` once, at the first every-5th-tick read that finds the PR in the queue (a queued reading also restarts the idle count, so while each 5th-tick read answers queued the PR does not expire), and stops on a dequeue as above. The wait is bounded two ways. More than 5 consecutive wait ticks (the 6th) with no pending REQUIRED check (a required check that does not exist yet, such as the `test` aggregate before its shards finish, counts as pending while any check is still running) print `[ship.phase7.queue_wait_expired]` and fall back to the BEHIND auto-sync for the rest of that poll (this poll's last queue read did not show the PR queued: keep the Monitor running, diagnose with the dequeue reference and the PR timeline, record the strict up-to-date question in the final report, and do not change the ruleset; the fallback `--step` itself skips a PR that is in the queue and fails closed on an unreadable queue read). `MAX_POLL_MIN` caps a PR whose required checks never settle or whose state keeps flapping (any tick that is not a wait tick restarts the idle count). Every unreadable answer falls toward today's sync (in the fence; the standalone script's rules read is the one exception, see Standalone guard below): a failed rules read or an empty required-check set leaves queue mode off for the poll, a failed armed read ends the wait for that tick (that tick syncs as today), and a failed checks read counts as idle. A DIRTY-derived BEHIND, a repo with no queue rule and a poll with auto-sync disabled behave exactly as before. Waiting does not consume `MAX_BEHIND_SYNCS`. Accepted residuals (ADR-270 amendment 2026-10-07): some required contexts (`tenant-integration-required`, `vendor-pin-required`) post a PASS on `merge_group` without re-running their suites, so in queue mode their only real run is the PR-time one against the PR-time base (the sync used to re-run the PR-event versions on a fresher base); and a dequeue during the wait is found by a current removal event on the next 5th-tick read, because the seen-queued marker is only written by `--step`.

**Standalone guard (2026-10-09, PR 9839).** `sync-pr-behind.sh <PR>` (the standalone loop) now enforces the rule above itself: when GitHub reports the PR BEHIND (not DIRTY), auto-merge is armed and `main` has a `merge_queue` rule (selected by `.type`, one read of up to 100 rules), it prints `kind=queue_wait rc=0` and exits 0 with nothing fetched, merged or pushed. A rules read that still fails after `PR_QUEUE_ATTEMPTS` tries (default 2, as for the queue read) or answers non-numeric is `kind=gh` (exit 4) with the cause in the line. This is the one place the script FAILS CLOSED on an unreadable rules answer: the fence above falls toward sync, but a standalone run has no poll behind it and an unknown answer is not a yes (the cost is a visible, named stop on a host whose token cannot read repository rules; the sanctioned sync is then the Phase 7 poll's expiry fallback). The incident: an agent hand-wrote a poll loop that treated BEHIND as an error and ran the script after `gh pr merge --auto` and before the enqueue (one push landed after the arm, 12 minutes in), restarting PR CI for nothing; the old prose scoped the ban to a poll that had already emitted `[ship.phase7.queue_wait]`, a marker a hand-written loop never emits, so the executable now refuses on the facts. Boundaries, stated so they are not rediscovered: (1) `--step` is the fence's call and is not guarded: the fence owns the rule, armed, expiry and DIRTY-derived-BEHIND decisions, and its expiry fallback must keep syncing (a hand-rolled loop that calls `--step` directly stays possible; follow-on tracked in #9869). (2) Base is `main`, as everywhere in the script. (3) The script does not read required checks: the fence sets `QUEUE_RULE=0` on a repo with no required checks and exits on a red required check, but the script answers `queue_wait` for any armed BEHIND PR; the refusal text therefore says to push a fix for a red check and routes to [merge-queue-dequeue.md](./merge-queue-dequeue.md) ("Armed and green but never enqueued") instead of promising a merge. (4) A DIRTY that is only GitHub's recompute lag after `main` moved still syncs. (5) The standalone answer has no expiry: the bound is re-arming the Phase 7 poll, whose fallback sync is the sanctioned one. The text surfaces say the same thing in one phrase: "when `main` has a merge queue and the PR is armed (the Phase 7 poll prints `[ship.phase7.queue_wait]`)" — a fact, not a marker only the Phase 7 fence prints; it holds for a BEHIND reading only. Surfaces not edited because they sit in the byte-ceilinged fences or outside the armed-BEHIND class: the fence `behind_no_sync` line (its standalone call now answers `queue_wait` on an armed PR, which is correct: fix the poll precondition and re-arm), `monitor-pr-checks.sh`, and `review/SKILL.md`'s DIRTY recovery.
