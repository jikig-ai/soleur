# Monitor hygiene for CI, release and deploy watches

Moved out of `ship/SKILL.md` Phase 7 to stay under the SKILL.md body ceiling (ADR-229): the text is unchanged except for links rewritten as paths and the positional words ("above") replaced by the sections they named; SKILL.md keeps a one-paragraph pointer. Read this before arming a post-merge, release or deploy Monitor, or a poll that waits on a set of runs.

**A Monitor must never HOST the work it watches — launch the work detached and let the watch only READ its completion artifact.** A long run placed in the Monitor's own command dies when the watch expires (`timeout_ms`, 30 min max): no rc file, no marker, a vanished runner — the documented *reap* signature, UNRESOLVED, never a result. Launch detached (`setsid nohup <script> &`, rc written as the script's last act) and the run survives an expiry. **Why:** #8233 — a 35-minute battery run as the Monitor's command was reaped at 30 minutes; relaunched detached, it completed. See `knowledge-base/project/learnings/2026-09-17-the-watcher-and-the-watched-shared-a-lifetime.md`.

**A poll whose population can SHRINK needs a floor, and must require the run it waits for to be PRESENT.** `pending == 0` is satisfied by an empty set — a query that stops returning your runs reports ALL-SETTLED having examined nothing. Record the largest population seen, refuse to settle below it, and require the run you wait for (deploy arm, release job) to be present, not merely non-failing.

**The cause is almost always `--limit` truncation, not the branch filter — CORRECTED 2026-09-17 after measurement.** An earlier revision blamed `--branch main --commit <sha>` and prescribed dropping `--branch` — FALSE mechanism, no-op remedy: `gh run list` with and without `--branch` returned identical counts on two `main` commits (every run, `push` included, carries `headBranch: main`). What actually happens: newest-first ordering under a `--limit`, so on a busy commit the release runs are crowded off the end by unrelated `issues`/`issue_comment` traffic (measured: `--limit 100` → `push=0`, `--limit 300` → `push=8` of 131). Raise the limit, paginate, or filter `--event push` / `--event workflow_run`; dropping `--branch` under the same limit rebuilds the identical watcher. **Why:** #8233 — a release watch reported 10 release runs then 0, one poll short of declaring a deploy settled over nothing.

**Run every POST-merge Monitor with its shell in a detached `origin/main` worktree (step 2 of the merge → deploy protocol at the top of `ship/SKILL.md`) or `/var/tmp`, never `cd`'d into the feature worktree.** The pre-merge Phase 7 poll in `ship/SKILL.md` is the exception: its BEHIND arm pushes the checked-out PR branch, so it runs from the PR worktree (from a detached HEAD it reports `kind=detached_head` and stops). After the merge any session's `cleanup-merged` can reap that worktree, and a monitor `cd`'d into it dies with `fatal: Unable to read current working directory`. **Why:** #8136 — the #8074 release watch died this way while the release was red.

**A watch lasts at most 30 minutes, so a longer wait is a chain of bounded watches.** Arm each with `timeout_ms: 1800000` (the default is 5 minutes) and give the watched command a bound meant to fit inside it (an overrun lands on the interrupted re-arm below). A read-only poll such as `deploy-arm.sh find` may run as the watch's own command: this is not hosting, because the deploy runs in GitHub Actions and `find` only reads it, so killing it loses nothing. Give it `find --wait 25 <full-merge-sha>` and re-arm a fresh watch when the line starts with `ARM=none REASON=timeout` (the 25 polls ran out), when it is `ARM=none REASON=error CAUSE=interrupted` (the watch expired and killed the call), or when the watch ends with no line, up to 5 times; any other line is final. After the fifth, report the deploy as unconfirmed and do not run `served`. Never run `find --wait` as a foreground Bash call: the default 120 polls can wait about two hours, past the Bash tool's 600 s cap. **Why:** PR #12645 — a foreground `find --wait` was killed at the Bash timeout (learning `knowledge-base/project/learnings/2026-11-11-a-census-keyed-on-the-client-name-missed-every-call-split-across-lines.md`, error 18).

## Run poll: stdout and stderr

Moved out of the post-merge release-run poll in `ship/SKILL.md` (Step 3, "Why this pattern") and rewritten when the poll stopped merging stderr into its answer (#12697).

**The poll emits on every state change** (so `queued → in_progress → completed` produces three events) **plus a heartbeat every 6th poll** (~3 min), so the monitor never looks stuck. `.conclusion // "-"` keeps a second token while the run is in progress: a null conclusion would render as a trailing space that looks like silence.

**stdout is the answer and stderr is a diagnostic, so the two never share a capture.** gh 2.106.0 (measured 2026-11-25) prints an 8-line `hint: … gh event listen …` block on stderr, with rc 0 and before stdout, for `gh pr view` of an open PR, `gh run view` of an in-progress `pull_request` run and `gh api repos/O/R/pulls/<N>` (every sub-path); a merged PR's view and a completed run's view print none, and no documented env var or config key turns it off. For this run poll the change is hygiene, not a timeout fix: a finished run prints no hint, and the line-wise `grep -qE "^(completed|fetch-error)"` would match a `completed` line under `2>&1` anyway. What `2>&1` costs here is noise: while the run is in progress every tick's answer carries the hint, so the Monitor stream fills with it and the hint text takes part in the `$r != $prev` change detection. The Phase 7 merge poll is where the merge was fatal: an exact `$s == "OPEN BEHIND"`-style comparison cannot match a value that starts with `hint:`, so it lost every OPEN arm (BEHIND auto-sync, the dequeue read, the required-set read). So stderr goes to a per-poll file: one `mktemp` (`/dev/null` when it fails, so nothing ever runs `rm` on `/dev/null`), truncated by each call's `2>` and removed by the loop's single EXIT trap. Only a failed call reads it. `fetch-error:` carries the first line that is neither the hint nor its indented tail, cut to 200 characters by substring expansion (`${m:0:200}`) and never by `| head -c` (which SIGPIPEs the writer under pipefail). With no such line it carries `rc=<rc>`. The Phase 7 merge poll's `gh_err_line` also drops every byte outside printable ASCII, tab and newline before that filter (`LC_ALL=C tr -cd`, so an ESC, BEL or CR never reaches a Monitor line); these run polls do not yet, because the strip does not fit under the `ship/SKILL.md` byte ceiling.

**The exit clause.** `grep -qE "^(completed|fetch-error)"` breaks on a terminal state. A `fetch-error` breaks too, so the caller surfaces the API failure instead of polling forever against an outage. Do not "simplify" the read to `2>/dev/null` with a bare rc: that drops the error text operators and fixtures read.
