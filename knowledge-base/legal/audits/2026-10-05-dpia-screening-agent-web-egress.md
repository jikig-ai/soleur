# DPIA Screening Memo — Agent Web Access (PA-2 amendment, #9534)

**Question screened:** does Article 35(1) GDPR require a full Data Protection
Impact Assessment for the opt-in open-web-egress sub-purpose appended to
Processing Activity 2 (a workspace "Agent web access" toggle that routes
entitled hosted agent sessions' HTTPS traffic through a dedicated Squid
CONNECT-only egress gateway)?

**Conclusion: a full DPIA is NOT required.** The processing is opt-in at the
workspace-owner grain (consent, Art. 6(1)(a)), default-OFF, fail-closed on
every resolution/spawn path, and reversible live (toggle-off kills the
session forwarder + deletes the token file). Three **named accepted
residual risks** are recorded below; re-screening triggers are pinned at §3.

## 1. Screening against the Art. 35(3) indicators and WP248 rev.01 criteria

| Criterion | Finding |
|---|---|
| Systematic/extensive **automated evaluation with legal or similarly significant effects** (Art. 35(3)(a) / Art. 22) | **Not met.** The feature transports traffic; it evaluates no person and takes no automated decision about anyone. The gateway's allow/deny applies to *destinations*, not data subjects. |
| **Large-scale processing of special categories** (Art. 35(3)(b) / Art. 9) | **Not met as systematic processing.** An entitled agent could in principle transmit Art. 9 content a user placed in their workspace — but the transmission is user-directed (the owner opted in; the agent acts on workspace content the owner controls), destinations are unenumerated public hosts, and no recipient processes it on Jikigai's behalf. The AUP already prohibits submitting Art. 9 data via the platform. Residual (a) below. |
| **Systematic monitoring of a publicly accessible area** (Art. 35(3)(c)) | Not met. |
| WP248: **vulnerable data subjects / imbalance** | **Not met.** The data subjects are Web Platform end-users and their workspace owners — the same population as the parent Activity, and the feature is *their* opt-in. No involuntary subject enters through this path. |
| WP248: **innovative use of technology** | **Partially engaged** (agent-initiated arbitrary egress is a novel capability for the platform). Offset by: the capability is industry-ordinary for hosted dev agents; the gateway is a conventional CONNECT proxy with a deny-set, not an inspection device; and the consent gate is explicit with risk disclosure at the toggle. |
| WP248: matching/combining datasets; transfers outside the EU; prevents exercise of rights | Matching: none — the gateway makes no joining of datasets; its logs are destination+workspace attribution only. Transfers: **no new contracted recipient** — destinations are arbitrary public hosts the agent requests; the only Jikigai-operated log path lands on the existing Better Stack EU pipeline (PA-8). Rights: unaffected — an Art. 15/17 export or erasure operates identically; the toggle state is a workspace row. |
| WP248: **physical access / cross-border systematic monitoring** | Not met. |

At most one WP248 criterion is partially engaged (innovative technology);
WP248's own threshold ("in most cases … two criteria") is not met, and no
Art. 35(3) indicator is met at all. The consent gate, owner-only write
(P0001-enforced SECURITY DEFINER RPC), member-visible locked state,
per-session token lifetime, credential quarantine in-sandbox, and
fail-closed degradation together keep residual risk below the Art. 35(1)
"high risk" line. This screening memo + the PA-2 amendment is the
proportionate Art. 24/25 record.

## 2. Named accepted residual risks

Accepted **by name**, each with its owner-visible failure mode.

**(a) Exfiltration by a compromised or prompt-injected agent in an entitled
workspace.** This is the feature's headline risk and is deliberately NOT
mitigated away — it is disclosed to the owner verbatim at enable time
("A compromised or prompt-injected agent could send workspace data to
external hosts"). Mitigations that bound but do not eliminate it: the
`credentials.envVars` deny census + `denyRead` additions mean an entitled
session has **no readable credentials** in-sandbox (API keys, BYOK service
tokens, GH/git auth are all unset/denied for sandboxed commands), so the
exfiltratable payload is workspace *content*, not workspace *secrets*;
gateway destination denies exclude metadata/internal ranges; every CONNECT
decision is logged with workspace attribution. Phase B (#9543) restores
credentialed operations through a broker rather than readable secrets.

**(b) Control-plane bleed-through.** Measured in the Phase-0 spike (spec
TR7): the SDK's own control-plane traffic (Anthropic API, MCP proxy,
telemetry intake) transits the forwarder/gateway even with `NO_PROXY`
enumerating those hosts — the runtime does not exempt them. The gateway
permits them as ordinary public CONNECTs; they are TLS end-to-end, so the
gateway sees only CONNECT metadata, logged under the workspace token.
Accepted as audit-attribution noise, not a security boundary breach; the
session token is never presented to third parties — it authenticates only
the loopback forwarder and the internal gateway.

**(c) Token-in-env visibility within the platform.** The session token rides
the spawned-CLI env (`HTTP(S)_PROXY` URL credentials). It is *not* injected
into the sandboxed child's env (SRT substitutes its own per-session creds
on the in-netns hop — measured). A same-UID process on the app container
could read the token from the subprocess env — accepted: token validity is
bounded to the session's lifetime and deleting the token file revokes it;
the token grants only "use this session's forwarder," not data access.

## 3. Re-screening triggers (pinned)

On any of these, re-run this screening before merge:

- **(t1)** The toggle becomes non-opt-in, member-writable, or default-on.
- **(t2)** The deny census or `denyRead` additions are weakened for
  entitled sessions (Phase B broker lands under its own review — #9543).
- **(t3)** The gateway gains content inspection (TLS bump) or its log
  begins carrying request paths/bodies rather than CONNECT metadata.
- **(t4)** The destination policy gains a user-defined *allowlist
  relaxation* mechanism that bypasses the deny CIDRs.
- **(t5)** WebSearch or another server-side tool is coupled to the grant.
- **(t6)** First observed exfiltration incident through an entitled
  session, or the audit-log viewer (#9545) lands.

## 4. Addendum — 2026-11-09 (#12469): re-screening for the entitled-session GitHub read tools

This addendum is append-only; sections 1 to 3 above are the 2026-10-05 record and are not rewritten. It is written in the present tense on the footing that the change lands on merge: it fires on the merge of PR #12465 (which closes #12469) and describes no state that exists before it.

**Trigger.** Re-screening trigger **(t5) fires**: tools are coupled to the grant. An entitled hosted session (Agent web access on, the credential quarantine in force) now receives six server-side, read-only GitHub tools: `github_list_pull_requests`, `github_read_pr`, `github_read_issue`, `github_read_issue_comments`, `github_list_pr_comments` and `github_read_ci_status`. They exist because in-sandbox `gh` has no credentials in an entitled session (ADR-278 Decision 5), so reads were lost with the writes. **Trigger (t2) does not fire**: the deny census and `denyRead` additions are unchanged, and the installation token runs in the dispatch process and never enters the sandbox (ADR-278 amendment and ADR-311 addendum of the same date).

**Conclusion.** A full DPIA remains NOT required. The processing is the same owner-opted-in, default-off, fail-closed sub-purpose, and the tools add a read path from the owner's own connected repository, not a new recipient or a new data subject population beyond the third-party authors named below.

**Residual (a): accepted with a named widening, narrowed by the public-repository gate.** Third-party issue, pull-request, comment and CI text becomes agent input in a session that has open egress. This widens residual (a), because that text is now co-resident with an egress path. The widening is bounded as follows.

- The tools register only when the connected repository is verified PUBLIC (one bounded lookup; any error, timeout or missing field is treated as not public: it fails closed under its own reason, `visibility-unknown`). A repository that is private at registration never gets the tools and keeps today's behaviour; the flip-to-private residual named below is the exception.
- Widening to private repositories needs a new CLO ruling and an owner-acknowledgement flow before it can ship; it is tracked in #12471.
- The repository, owner and installation are closed over server-side; the model never supplies them, and each call re-checks repository identity (owner and repo) and the stored installation id, failing closed on a mismatch or when it cannot be confirmed. **Named residual:** visibility is verified once at cold registration (one bounded `GET /repos/{owner}/{repo}`), not per call, so a public-to-private flip during a live conversation keeps the tools serving until the next cold start (CTO ruling D2; private repositories are #12471). Likewise, toggling Agent web access off mid-conversation tears down the forwarder but leaves the read tools registered until the conversation ends.
- The tool results carry untrusted-content framing. That framing covers comments and CI text as well as titles and bodies.
- `redactGithubSourcedText` is applied to the title and body fields only. User logins, assignees, label names, the milestone title, `head_ref` and `base_ref`, and the CI run name, branch, sha and url are only stripped of invisible characters and length-capped. In both cases it is **data minimisation**. It is NOT a confidentiality control and NOT an anti-exfiltration control: it does not stop an agent from sending what it has read to an external host.

**Point-in-time production read, dated 2026-11-09.** Exactly one workspace has `web_egress=true` (the jikig-ai/soleur dogfood workspace, with egress audit rows since at least 2026-10-24). Its owner is the requester of this change, and its connected repository is public. On that footing no re-acknowledgement gate is added for already-enabled workspaces: the new toggle copy ships in the same change as the tools and is shown before every future enable. **Re-evaluate if another workspace enables Agent web access before the copy ships.** The DPIA conclusion above is a one-workspace conclusion: it is re-screened, with the Art. 14 condition below, when a second workspace has the tools registered.

**Art. 14 and the lawful basis.** The third-party authors are not individually informed by this change. The CLO agent attested the Art. 6(1)(f) legitimate-interest assessment (written in the `article-30-register.md` amendment of the same date) and settled the Art. 14 position on 2026-11-09: Art. 14(5)(b), disproportionate effort, with the published register, this addendum and the Privacy Policy Section 8.1 carve-out as the appropriate measures. The weakest points are named there (commercial purpose; the carve-out is not worded for issue, pull-request and comment authors or for the hosted agent's reads; the `jikig-ai/soleur` population is already engaged and undischarged under PA-31 and PA-32, #7120). One condition remains and is tracked in #12487: before a workspace other than the Jikigai-owned one has the tools registered, the Section 8.1 carve-out is widened and a per-login suppression route is decided. Authority: `knowledge-base/legal/audits/2026-11-counsel-review-12469.md`. This matches the register.

**Readers.** Workspace members also receive the tools in an entitled session, although only the owner consented to the toggle. Members are named here as readers of the public repository's issue, pull-request and CI text through the agent.

**No scope-grant gate.** There is no scope-grant gate on this path. Scope Grants governs scheduled-template action classes, not interactive reads. The workspace toggle is the only control, and no document may state otherwise.

**Unchanged.** The privacy policy and the data protection disclosure are not edited by this change (CLO ruling, 2026-11-09). Writes, workflow logs, private repositories, read-tool refinements and legacy redirect handling are deferred to #12467, #12468, #12471, #12470 and #12472.
