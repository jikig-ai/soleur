# Counsel review audit — #7829 / PR #7914

Artifact in scope: the 2026-09-07 amendment to Art. 30 PA-23 limbs (c) and (g)
in `knowledge-base/legal/article-30-register.md`. No `[DRAFT — pending
CLO/counsel review]` markers were added by the PR, so nothing was cleared; this
is the substantive attestation.

## Q1 — Is amended limb (c) accurate and complete?

**Accurate. Complete but for one column.** Every factual claim verified against
the migration body:

- Five refusal branches, each persisting before `RETURN NEXT`, and the enum
  values `{revoked_post_grace, expired, consent_withdrawn, hourly_cap_exceeded,
  daily_cap_exceeded}` match the widened CHECK constraint in §1 of the migration.
- `founder_id = p_caller_user_id` (grantee) on all five refusal INSERTs;
  `v_row.grantor_user_id` only on the admit path. The claim that the rows are
  grantee-attributed holds.
- `ownerField: "founder_id"` with no `additionalOwnerFields` confirmed at
  `server/dsar-export-allowlist.ts` (`audit_byok_use: { ownerField:
  "founder_id", article: "15" }`), so the bundle-shift statement holds.
- The retraction of the prior text ("described a category of data that was not
  in fact being processed") is correct: the 084 body carries no `EXCEPTION WHEN`
  handler, so the pre-`RETURN` INSERTs were discarded with the transaction.

**F3 (recommended, non-blocking):** the enumeration omits `invocation_id`, which
every refusal INSERT writes and which is the row's uniqueness key
(`ON CONFLICT (invocation_id)`).

## Q2 — Is the (g)(5) recharacterisation defensible, and is lawful basis stated?

**Defensible, and it is the honest characterisation.** `persistTurnCost` calls
the RPC after `messages.create`, fire-and-forget; the provider is already
charged when the refusal is decided. A control that records rather than prevents
is an Art. 5(1)(d) accuracy / Art. 5(2) accountability measure, not an Art. 32
availability-of-spend control, and the register saying so plainly is what an
Art. 30 record is for. Withdrawing an overstated Art. 32 claim is a correction
in the direction of accuracy — the same class as the 2026-09-03 PA-13 retraction
already on record.

**Lawful basis: adequately stated where it is stated, but not in the register.**
PA-23's table carries no lawful-basis limb (Art. 30(1) does not require one), so
the amendment's "lawful basis … unchanged" is a statement about nothing inside
this table. The basis is declared in the migration header (`LAWFUL_BASIS: Art.
6(1)(b) — billing accounting for a delegated key`). That is sound for the
grantor (whose key paid). For the **grantee** the row is an internal attribution,
not a debt — no money is collected from the grantee — so Art. 6(1)(b) is the
weaker fit and Art. 6(1)(f) (accurate accounting and abuse-boundary
accountability within a workspace the grantee joined by signed side letter) is
the better-fitting basis. No change is required in this PR: the register does not
record bases per activity, and the grantee's processing is covered by the same
declared basis as the admitted rows. Recorded as a re-evaluation trigger rather
than a condition.

## Q3 — Are (d)(e)(f) genuinely unchanged?

**(e) Transfers — unchanged, true.** No new third-country flow; the refusal rows
never leave Supabase.

**(d) Recipients — the CATEGORY is unchanged, but the limb was already
incomplete, and mig 137 makes the omission material.** Verified at
`059_workspace_keyed_rls_sweep.sql`: `DROP POLICY … audit_byok_use_owner_select`
followed by `CREATE POLICY audit_byok_use_workspace_member_select … USING
(public.is_workspace_member(workspace_id, auth.uid()))`. The grantor
additionally reads these rows through the Funded pane's service client
(`server/byok-delegation-ui-resolver.ts` line 1, `createServiceClient`), which
bypasses RLS. Limb (d) names only Anthropic PBC and Supabase Inc. The sibling
PA-24 (d) names co-members as recipients for exactly this shape. **F2
(recommended).** It is not blocking because the recipient *category* predates the
change and because the user-facing disclosure already exists: the register's own
cross-cutting co-member entry names rows where `audit_byok_use.founder_id =
<co-member>.id`, disclosed at DPD §2.3(u) and Privacy Policy §4.11.

**(f) Retention — "unchanged" is true as a delta and should not be read as an
affirmation.** The 7-year period is untouched. Two observations, neither
blocking: (i) the Art. 17 path for these NEW rows is not the two
`anonymise_byok_delegation*` RPCs named in (f) but the `founder_id ON DELETE SET
NULL` cascade of migrations 065/066 — erasure yields anonymisation-in-place, with
`workspace_id`, `delegation_id` and cost surviving in the WORM ledger; (ii) the
same table carries three different retention statements across the register
(PA-13 (f) "12-month sweep", PA-16/PA-21 (f) "90-day", PA-23 (f) "7 years").
Both predate this PR and belong to #7921.

**Different data subject, same limbs — is that sustainable?** Yes. (b) already
names both grantor and grantee as data subjects, so the refusal rows fall inside
the declared subject set; what moved is which subject a given row identifies, and
limb (c) records exactly that.

## Q4 — Is deferring the DSAR shift to #7926 correct?

**Correct.** Art. 15 completeness for the grantor is a determination, not a
gap the register must close to be lawful on merge. The register's job is to
record the processing truthfully, and limb (c) records the shift explicitly and
in both directions. #7926 is open, states the three competing readings, and its
"Done when" already binds the outcome back to either
`dsar-export-allowlist.ts` or PA-23 (c). Nothing has to land in this PR. Note
for the record: the grantor is not left blind in-product — RLS co-member SELECT
and the Funded pane's service client both keep the rows visible to them; only
the export bundle is at issue.

## F1 — the one thing that must change

PA-23 limb (g), measure (9) as drafted:

> **(9) Personal-cap isolation (new, 137):** `record_byok_use_and_check_cap`'s
> founder SUM gains `AND delegation_id IS NULL`, …

The shipped filter is `AND attribution_shift_reason IS NULL`
(`137_byok_cap_breach_audit_row.sql` §3, and asserted by
`supabase/verify/137_byok_cap_breach_audit_row.sql`). `AND delegation_id IS NULL`
is the alternative the migration header and ADR-208 record as **rejected as
over-broad**. A register that names a rejected predicate as a technical measure
in force asserts a control that does not exist — the drift class of PR #4353
and PR #4558. The stated *effect* of the measure is correct; only the predicate
is wrong. Replacement text is quoted in the PR verdict and must be applied before
merge.
