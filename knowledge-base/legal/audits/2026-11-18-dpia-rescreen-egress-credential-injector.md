# DPIA Re-screen — Credential injector on the egress hop (#11637, trigger t3)

**Question screened:** Does Art. 35(1) GDPR require a full DPIA for terminating TLS at the egress hop of web-egress-entitled agent sessions, so that a Jikigai-run injector can read each request to the GitHub hosts, decide whether to attach the workspace's GitHub credential, and record write approvals? If not, on what conditions may the broker (a) merge dark, (b) turn on for Jikigai-owned workspaces, and (c) turn on for tenants?

## 6. ePrivacy and secrecy of correspondence

Ruled by CLO agent, 2026-11-18:

For the self-run, inject-hosts-only design, terminating TLS at the hop does **not** engage Art. 5(1) of Directive 2002/58/EC, its French transposition (CPCE L.32-3 and L.34-1), or Code pénal art. 226-15. The grounds are these.

1. The decryption happens inside the sending endpoint's own system, on the same host. It happens before the request crosses a public communications network, on a TLS session that the agent's own client opened to a trust anchor only that session holds. The decrypted request is then passed, on the same host, to an approval hook that in the spike is one process shared by the host's sessions (section 2). The onward connection to GitHub is a fresh, verified TLS session.
2. Jikigai is the sender's operator, not a person "other than users". The agent Jikigai runs composes the request, at the workspace's direction, from content Jikigai already processes. A sender's own software reading the sender's own outgoing request is not interception.
3. The requests are machine-to-API calls to a code host. They are not interpersonal communications, and the platform is neither a conveyance service nor a number-independent interpersonal communications service, so the CPCE operator duties do not attach.
4. Art. 226-15 needs correspondence and bad faith. An owner opt-in with disclosure excludes bad faith. During (B) the disclosure is gate B-11's written notice; during (C) it is gate C-3's copy.
5. Art. 5(3) is not engaged: the CA goes into the trust store of Jikigai's own sandbox, not into a user's terminal equipment.

**This ruling stops holding** if any of the following happens: a third party terminates the TLS (any managed platform; ADR-325's CLO gates then also apply); a host carrying interpersonal communications (mail, chat, messaging) joins the inject set, or termination widens beyond it; decrypted content is kept or used for anything other than the vend decision and the approval record; or response bodies are requested, or anything from a response is stored.

**Counsel.** The question does not block (A) or (B). (C) is this memo's first-arms-length re-review trigger, and that external re-review must answer Q-1 before (C).

> **Q-1 (for outside counsel).** Jikigai SARL (France) runs AI agent sessions for SaaS customers on its own EU servers. When a workspace owner enables it, a Jikigai-run proxy on the same host terminates the TLS connection that the agent's own git, gh or HTTP client opens to github.com, api.github.com, uploads.github.com and codeload.github.com. The proxy reads the request (method, path, query, headers, body) and passes it to a Jikigai approval process on the same host, which decides whether to attach the customer's GitHub credential and whether owner approval is needed; the proxy then re-encrypts to GitHub with certificate verification. Response bodies are not read or stored; the approval process may receive each response's status and headers and passes the response on unchanged. What is kept: (a) for each write request, an approval record holding the workspace, conversation and requesting user, the repository where one is resolved, and, by type of request: for a git push, the ref updates (old and new commit identifiers), capabilities and push options; for an API write, the method, path, full query string and a hash of the body; for a GraphQL write, the operation name, type and fields and hashes of the document and variables (the action text is removed from the live record 30 days after the decision and remains in database backups for their retention); (b) for every request, reads included, a log entry with the session, request identifier, host, method, class of request, policy rule, outcome and approval identifier, and no path or content; (c) for every connection the session opens, to any host, a log entry with the session, host and port. (1) Does this engage Art. 5(1) of Directive 2002/58/EC as transposed in France (including CPCE L.32-3 and L.34-1), or Code pénal art. 226-15, as to the customer, its workspace members, or third parties whose content is carried? (2) If so, is the owner's opt-in sufficient consent, or is each inspected member's consent required? (3) In a team workspace where Jikigai is processor, must the Art. 28(3) instrument name this inspection as an instruction?

## 8. Named accepted residuals (state B)
