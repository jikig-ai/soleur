# DPIA Re-screen — Credential injector on the egress hop (#11637, trigger t3)

**Question screened:** Does Art. 35(1) GDPR require a full DPIA for terminating TLS at the egress hop of web-egress-entitled agent sessions, so that a Jikigai-run injector can read each request to the GitHub hosts, decide whether to attach the workspace's GitHub credential, and record write approvals? If not, on what conditions may the broker (a) merge dark, (b) turn on for Jikigai-owned workspaces, and (c) turn on for tenants?

## 1. What changed in the facts of the 2026-10-05 memo

| Fact in the 2026-10-05 memo | Position under the #11637 design (from first flag-on unless marked) |
|---|---|
| The gateway is "a conventional CONNECT proxy with a deny-set, not an inspection device"; control-plane traffic is "TLS end-to-end, so the gateway sees only CONNECT metadata". | For four hosts (`github.com`, `api.github.com`, `uploads.github.com`, `codeload.github.com`), a per-session iron-proxy v0.56.0 (`tls.mode: mitm`) terminates the agent client's TLS using a per-session CA that only that session trusts. It reads the request and re-establishes TLS to GitHub with verification on. Every other host stays tunnelled end to end through the unchanged forwarder and Squid gateway (criterion 2, measured in the harness only). iron-proxy terminates **every** tunnel it receives, so the selectivity rests entirely on the per-session router sending it only inject-host CONNECTs (ADR-325, tracer item 2). |
| Logs are "destination + workspace attribution only". | iron-proxy's own JSON audit line carries at least method, host, **path**, action and status (`lib/iron-audit.py` reads those fields from it). The path names the repository and the resource. This is the second limb of t3. The hook's markers (`SOLEUR_EGRESS_VEND`, `SOLEUR_EGRESS_VEND_REFUSED`, `SOLEUR_EGRESS_CONNECT`) carry session id, request id, host, method, class, rule, reason, approval id and a 12-character hash prefix. They carry no path, and no secret or body (criterion 6). |
| An entitled session has no readable credentials in-sandbox, so the exfiltratable payload is workspace content, not secrets (residual (a)). | The credential is still not readable in the sandbox or by the agent's file tools (criterion 1). But it is now **usable**: reads of allowlisted repositories get the credential with no row, so what an injected agent can exfiltrate grows to include anything readable through the vended credential. Writes stay gated. |

Their CONNECTs then pass through the forwarder and Squid, so GitHub hosts start appearing in the PA-37 rollup. This is not new in kind. |

## 5. Conclusion

Ruled by CLO agent, 2026-11-18:

- **(A) Dark, flag-off merge:** no decryption, no new rows and no new log lines occur. A full DPIA is **not required**.
- **(B) Flag-on limited to Jikigai-owned workspaces:** one criterion is engaged (8) and one is partly engaged (3). The controller and every data subject other than third-party repository authors are Jikigai itself. A full DPIA is **not required, CONDITIONAL** on the B-gates in section 7. If any B-gate stops holding, the result is (C).
- **(C) Flag-on in any workspace Jikigai does not own:** criterion 8 is engaged, criteria 3 and 7 are partly engaged, and the scale limb falls. That reaches WP248's two-criterion threshold, and the "in most cases" discretion is not used: the processing is new in kind (the platform reading tenants' outbound traffic in plaintext). A full Art. 35(7) DPIA is **REQUIRED and must be completed before that flag-on**. It must also cover PA-38, whose screening is still owed (GDPR Policy section 9).

## 6. ePrivacy and secrecy of correspondence

Ruled by CLO agent, 2026-11-18:

For the self-run, inject-hosts-only design, terminating TLS at the hop does **not** engage Art. 5(1) of Directive 2002/58/EC, its French transposition (CPCE L.32-3 and L.34-1), or Code pénal art. 226-15. The grounds are these.

1. The decryption happens inside the sending endpoint's own system, on the same host and for the same session. It happens before the request crosses a public communications network, on a TLS session that the agent's own client opened to a trust anchor only that session holds. The onward connection to GitHub is a fresh, verified TLS session.
2. Jikigai is the sender's operator, not a person "other than users". The agent Jikigai runs composes the request, at the workspace's direction, from content Jikigai already processes. A sender's own software reading the sender's own outgoing request is not interception.
3. The requests are machine-to-API calls to a code host. They are not interpersonal communications, and the platform is neither a conveyance service nor a number-independent interpersonal communications service, so the CPCE operator duties do not attach.
4. Art. 226-15 needs correspondence and bad faith. An owner opt-in with disclosure excludes bad faith.
5. Art. 5(3) is not engaged: the CA goes into the trust store of Jikigai's own sandbox, not into a user's terminal equipment.

**This ruling stops holding** if any of the following happens: a third party terminates the TLS (any managed platform; ADR-325's CLO gates then also apply); a host carrying interpersonal communications (mail, chat, messaging) joins the inject set, or termination widens beyond it; decrypted content is kept or used for anything other than the vend decision and the approval record; or responses are inspected or stored.

**Counsel.** The question does not block (A) or (B). (C) is this memo's first-arms-length re-review trigger, and that external re-review must answer Q-1 before (C).

> **Q-1 (for outside counsel).** Jikigai SARL (France) runs AI agent sessions for SaaS customers on its own EU servers. When a workspace owner enables it, a Jikigai-run proxy on the same host terminates the TLS connection that the agent's own git, gh or HTTP client opens to github.com, api.github.com, uploads.github.com and codeload.github.com. The proxy reads the request (method, path, body) to decide whether to attach the customer's GitHub credential and whether owner approval is needed, then re-encrypts to GitHub with certificate verification. Responses pass through unread and unstored. Only a structured approval record is kept, for write requests (repository, ref or path, and a body hash). (1) Does this engage Art. 5(1) of Directive 2002/58/EC as transposed in France (including CPCE L.32-3 and L.34-1), or Code pénal art. 226-15, as to the customer, its workspace members, or third parties whose content is carried? (2) If so, is the owner's opt-in sufficient consent, or is each inspected member's consent required? (3) In a team workspace where Jikigai is processor, must the Art. 28(3) instrument name this inspection as an instruction?

## 8. Named accepted residuals (state B)

- **R1. Plaintext concentration.** One hook process receives the request plaintext of every entitled session on its host and holds the service-role and HMAC keys. A compromise of the hook exposes all of that in transit.
- **R2. Residual (a) widens.** A prompt-injected agent can read allowlisted repositories with the vended credential and send the content over open egress, with no human seeing each read. The bounds are the allowlist, token scoping (B-6) and gated writes.
- **R3. Read trail.** Per-request `SOLEUR_EGRESS_VEND` markers keyed to the session give a host and method trail of a user's agent activity, with no path.
- **R4. Free text in rows.** A REST query string or git push options can carry free text into `canonical_action`. It is removed within 30 days.
- **R5. CA scope.** Under RFC 5280 the CA's name constraint also covers `*.github.com`. Only the router and the iron-proxy `allowlist` keep other subdomains out of termination.
- **R6. Stale copy.** During (B), the toggle copy ("cannot use git remotes") is inaccurate for the flag-on workspaces. This is accepted because the only readers are Jikigai personnel, and it lasts until the production measurement lets the copy change (ADR-311 Decision 6).
