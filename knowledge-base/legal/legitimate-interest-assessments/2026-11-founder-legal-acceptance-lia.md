# Legitimate Interest Assessment — Founder legal-acceptance record (PA-40)

This LIA records the Art. 6(1)(f) three-part test for the founder legal-acceptance record (`legal_acceptance`) and its email-code challenge table (`legal_reauth_event`), Article 30 register Processing Activity 40, issue #12011 (PR-B, migration 184). It is the **standalone** assessment the CLO ruling of 2026-11-03 requires; it is not folded into the PA-38 assessment, because the retention and erasure rule here is the opposite of PA-38's. It must exist before the first real row.

**Stage.** The database record shipped dark (PR-B). PR-C (2026-11-05) adds the web screen behind the `approval-queue` flag: the founder sees the card, reads the text, and records a decision through an email-code check on the card (see Web screen below). The card is PROVISIONAL and stays behind the flag until counsel decides the open items. The flag is read without a workspace, so it is effectively global (every workspace), not per user; "operator first" is therefore a roll-out commitment and not something the flag enforces, and no real legal text is committed, so the card shows nothing to anyone today. Nothing reads the tables to enforce anything until PR-D. The feature is operator first. The only data subject assessed is the Jikigai operator. A customer founder is **not** assessed here; admitting one re-opens this document (Re-evaluation triggers).

> **Superseded 2026-11-05 (#12187, PR-D; fires on its merge), as to "Nothing reads the tables to enforce anything until PR-D.":** from the merge the check endpoint exists; once it is configured (#12196; until then it answers 503) it will read `legal_acceptance` and the ship hold gate will use the answer (see the Addendum at the end).

**What is processed (summary).** For each decision on a legal text: the founder's account id as a plain uuid with no foreign key, the text's key, version and sha256 hash (the text itself stays in a committed file, not in the database), the choice (accept, decline, request changes), an optional free-text change request of at most 1000 characters, the session identifier, the time the email code was accepted (Yes only), a database-computed checksum of the row and the creation time. The challenge table holds a server-issued intent (30 minutes) bound to user, key, text hash, version and session, which for a Yes is also the single-use email-code challenge (the confirmed code must be no more than 5 minutes old when the decision is recorded). The code is checked by the authentication service and stored in neither table. Full field list: PA-40 (c).

**Web screen (PR-C).** The card shows the text as the server holds it, the three choices (none pre-selected), and, before the founder decides, two notices: the card-level notice (what is kept after the account is deleted, who can read it, and the retention period) and the notice beside the free-text field (do not put personal data in the note). Both are the drafted wording of parts (c) and (c-2) of the DSAR and notice note. **The retention period inside the card-level notice is still "to be confirmed by counsel"**, so the card carries a number that counsel has not decided. For that reason the card ships behind the flag and PROVISIONAL, and no real row is to be recorded through it before counsel decides item 1 below. A Yes needs a code emailed to the address on the founder's account, confirmed on the card within 5 minutes; every choice needs a server-issued intent (30 minutes). The card states that an answer is final and that changing it means a new text version sent by the team; there is no undo button. The code is checked on a throwaway client whose session is discarded, so the founder's own session is unchanged, the address the code goes to is taken from the session only, never from the request, and the send step returns the same response for a known and an unknown address. A per-user ceiling on code attempts applies in addition to the 5 per challenge; it is in-process, per web host and resets on restart, so it is a soft brake and the database bounds (5 per challenge, 3 challenges per 15 minutes) are the hard limit. The Request changes note has no delivery path to the team until PR-D, although the card says it is saved with the decision. The card reports four kinds of events to the error tracker (an accepted row, a refused decision with a reason, a failed code send or check with the provider's error class, and a page that could not read its rows); a fifth, a row with no matching accepted event, is defined for the PR-D check endpoint and nothing emits it yet. The events carry identifiers and tags, never the text, the code, the address or the note.

## Purpose

1. **Evidence of a decision.** Jikigai needs to be able to show later who decided what on which exact text: that a founder accepted, declined or asked for changes to a given version of a legal text (identified by hash), and when. The interest is Jikigai's own and is concrete: legal texts are the basis of commitments to third parties, and a dispute about whether a text was accepted turns on this record.
2. **Confirmation that the person deciding is the account holder (Yes only).** An email code, single-use and bound to the text, reduces the chance that a stolen or left-open session is used to accept a text. This serves the founder as much as Jikigai.
3. **Keeping the record after the account is deleted.** The evidential value of purpose 1 would be lost if the record disappeared when the account does; the retention is to establish, exercise or defend legal claims (Art. 17(3)(e)).

The purpose is specific (a decision on a named text), explicit (this LIA, PA-40, and the notice that will be shown on the Request changes field) and legitimate (accountability for commitments, security of an acceptance).

**Not pursued:** profiling or scoring the founder, approval-rate analytics, use of the free-text note for anything other than reading it as a change request, model training, enforcement. Nothing in the product reads these tables to enforce anything at this stage.

## Necessity

1. **Alternative A — no record; rely on the git history of the text and the founder's recollection.** Rejected for purpose 1: the git history shows what a text said, not that a person decided on it, and which version.
2. **Alternative B — record the decision without a reauthentication step.** Rejected for purpose 2 only as to the Yes: a Yes is the choice that creates a commitment. A decline or a change request creates none, so no code is required for them.
3. **Alternative C — store the verbatim text in the database.** Rejected: only the sha256 is stored, so the table holds no copy of a legal text and the text's content is not duplicated into a second store.
4. **Alternative D — delete the record on account deletion.** Rejected for purpose 3: it removes the evidence at the moment a dispute is most likely to arise. This is the alternative that matters most to the founder, and it is weighed under Balancing.
5. **Alternative E — keep the record on account deletion but blank the founder id.** Rejected: the checksum covers the founder id and the table refuses every update, so blanking breaks the record's integrity check, and a record with no person attached no longer shows who decided, which is its only purpose. A **hash of the founder id** is no better: still a stable pseudonym, with the same linkability and less clarity.
6. **Alternative F — structured choice only, no free text.** Considered. The note is the only way to say what a founder wants changed. It is optional, capped at 1000 characters and trimmed; the notice asks the founder not to put personal data in it. Counsel is asked whether it should stay (item 4).
7. **Minimisation within the processing.** No name, email address or IP address is stored in either table. The fixed values (`method`, `surface`, `reauth_method`) record how the decision was made, not who the person is. The challenge table holds identifiers and counters only.

> **Superseded 2026-11-05 (#12187, PR-D; fires on its merge), as to "either table":** the same holds for the third table `legal_acceptance_ack` (acceptance id and an acknowledgement time; no name, email, IP address, founder id or note).

**Conclusion:** a write-once record keyed on a pseudonymous uuid, with the text held by hash, is the least intrusive design that serves purposes 1 and 3. Two parts are weaker on necessity and are flagged: the free-text note (item 4) and the persistence of the challenge rows (Residuals).

## Balancing

Per WP29 Opinion 06/2014 §III.3: (i) nature of the interests, (ii) nature of the data, (iii) reasonable expectations, (iv) impact, (v) safeguards.

### (i) Interests

Jikigai's interest: evidence of a commitment-bearing decision and the security of the Yes. It is a business interest, not a statutory one; the register does not claim a legal obligation (Art. 17(3)(b) is **not** relied on). The founder shares the security interest. The founder's contrary interest is in erasure of an account's data when the account is closed.

### (ii) Nature of the data and data subjects

At this stage one person, the Jikigai operator, who is the controller's principal and not a vulnerable data subject. The data are a pseudonymous uuid, a text identifier and hash, a choice and timestamps. Special categories are not sought; the note is the one place they could appear.

### (iii) Reasonable expectations

A person who is shown a card that says what is being decided and who then confirms a Yes with an emailed code expects the decision to be recorded. They do not necessarily expect it to be **kept after they delete the account**. That expectation gap is the weak point of this assessment; it is closed only by telling the founder, before they decide, what is kept and for how long. PR-C puts both notices on the card, before the choice, which is the mechanism this paragraph calls for. It closes the gap only in part: the retention period shown is still "to be confirmed by counsel", and the notice has not been tested with a reader other than the drafter. The wording of that statement (on the card and in the erasure reply) is owed and is drafted in the DSAR and notice note; the published privacy documents carry only a short draft-marked disclosure written ahead of the processing (see that note, part d), which is acceptable only while the data subject is the operator and must be replaced by final wording before any other founder is admitted.

### (iv) Impact

Low for the operator: a uuid, a choice, a hash and a timestamp, readable by the founder through their own session and by Jikigai engineering through the database owner role. The record does not feed a decision about the founder and no automated decision with legal effect is taken from it (no Art. 22 trigger). The materially adverse paths are: (a) free-text personal data kept past erasure; (b) linkability of the uuid to the person through other stores (user table backups, logs) until those age out; (c) the retention period being too long for a record whose claims never arise.

> **Superseded 2026-11-06 (#12187, PR-D; fires on its merge), as to "by Jikigai engineering through the database owner role":** the database-owner credential is held by the operator and by the production migration pipeline (a CI secret that runs the migrate and verify steps of the release workflow). No agent session is meant to use either, which is a rule and not a control.

### (v) Safeguards (full list in PA-40 (g))

- Write-once record: UPDATE, DELETE and TRUNCATE are refused; insert only through the recording function.
- The actor is the authenticated session, never a parameter; a runtime-audience token cannot record a decision.
- The founder reads only their own rows; `service_role` holds no privilege on either table; the read-only check function returns status, hash, time and a checksum-match flag, not the note.
- Every decision needs an intent issued by the Jikigai server for that user, key, text hash and web session (30 minutes; at most 3 new intents per 15 minutes), so a decision cannot be recorded for a text the server did not issue; a Yes also needs a single-use email code confirmed in the last 5 minutes (attempt cap 5).
- The text is held by hash, not copy. The card renders the text the server holds and sends back only the hash it showed, so the client cannot supply text.
- The email code is single-use, bound to user, key, text hash and session, voided by a resend, and checked on a throwaway client; the address comes from the session only, never the request, so the send step has no address-enumeration surface; a per-user attempt ceiling applies across keys (in-process, per host, resets on restart; the database bounds (5 per challenge, 3 challenges per 15 minutes) are the hard limit).
- Both notices are shown on the card before the choice; the card says an answer is final.
- Behind the `approval-queue` flag; with the flag off the page still shows existing rows but creates nothing and cannot record a Yes. The first real row is conditional on this LIA, the attestation record and counsel's decision on the retention period.
- Dark launch (the database record); the first real row is conditional on this LIA and the attestation record existing.

The read-only check function will also be reached through the HTTP check endpoint once it is configured (four fields, never the note).

## Art. 17 and Art. 21 handling

**Erasure.** The account-deletion saga does not touch `legal_acceptance`. The founder is told, in the erasure reply, what is kept (the row, with the uuid and without name or email), why (Art. 17(3)(e), Art. 6(1)(f)), for how long (the retention period once confirmed), who can read it (the database owner role; the read-only check function returns status, text hash, decision time and a checksum flag but not the note; the founder's own session no longer exists), and the rights to object under Art. 21 and to complain to the CNIL. Wording: DSAR and notice note, part (b).

**Why not Art. 17(3)(b).** No legal obligation requiring this record has been identified. Claiming (3)(b) would overstate the basis.

**Art. 17(3)(e) limits.** The exception covers retention needed for legal claims. It is stronger where a dispute is pending or foreseeable and weaker as a blanket justification for a fixed period. This is the central counsel question (item 2).

**Art. 21.** Because the basis is Art. 6(1)(f), the founder may object on grounds relating to their situation. An objection is assessed per request: Jikigai stops unless it shows compelling legitimate grounds that override the founder's interests, or the processing is needed for legal claims. Art. 17(3)(e) operates independently for the retention after erasure, so an objection does not by itself remove a row that is needed for a claim. Each objection and its outcome is to be recorded with the DSAR handling (`knowledge-base/legal/statutory-response-catalog.md#dsar`); that catalog has no Art. 21 section today, which is owed before a founder other than the operator is admitted.

## Residuals

1. **The founder id is pseudonymous, not anonymous.** Anyone who holds the user table, a backup or a log carrying the id can link the row to the person. The register and notices say pseudonymous and never anonymised.
2. **The checksum is not an external anchor.** It detects a changed row. A holder of database-owner access can rewrite a row and its checksum, and the check would still pass. `service_role` holds no table privilege and cannot; a holder of the service key can stamp an intent as code-confirmed without mailbox access (`mark_legal_reauth_verified` trusts its caller) but still needs a founder web-session token to record (ADR-319 residual risk). The external anchor (only a chain head, a sequence number and a date published, never the founder id or row content, ideally a signed git tag) is deferred and not built; the current per-row design has no chain or sequence, so the anchor design must also define what is published.
3. **The free-text note can carry personal data** despite the cap and the notice, and cannot be removed alone on erasure: it is inside the row the guard keeps and the checksum covers.
4. **Challenge rows are purged late and not on erasure.** `legal_reauth_event` intents expire by timestamp after 30 minutes (a Yes also needs the code confirmed no more than 5 minutes before the decision is recorded); rows older than 30 days are deleted whenever the next challenge is issued, so a row can outlast 30 days when no challenge is issued. **[Clarified 2026-11-08 (#12197; fires on the merge of the pull request that carries it): "challenge" here includes the intent opened for a Decline or Request changes, so the purge runs on every decision intent, not only when a code is requested.]** `user_id` has no foreign key and no erasure step deletes the rows, so they outlive the account until that purge. They are operational and have no evidential purpose after minutes; the 30-day figure is an engineering value, not an approved legal number, and deletion on erasure is not built.
5. **Backups.** The retention window of database backups is not measured here; a row removed in future may persist there.
6. **A holder of production credentials can mint a founder session** (ADR-319 property 3, CTO ruling). The email code lowers but does not remove this.
7. **Access after erasure is by the database owner role, plus the read-only check function.** The check function (`verify_legal_acceptance`, service_role) returns status, text hash, decision time and a checksum flag, never the note. That is the restriction the erasure reply promises; it is a role restriction, not a technical bar.

> **Superseded 2026-11-06 (#12187, PR-D; fires on its merge), as to Residual 7 ("Access after erasure is by the database owner role") and Residual 6 ("A holder of production credentials"):** the database-owner credential is held by the operator and by the production migration pipeline (a CI secret); no agent session is meant to use either, which is a rule and not a control. What else that pipeline credential set can mint (for example a founder session) is not assessed here.

> Drafted, not counsel-reviewed. This addendum fires on the merge of PR #12187. Until then the body above is the operative text and nothing below describes processing that exists. The body above is unchanged except for the marked supersessions.

**What changes.**

1. *A fourth purpose.* The check endpoint `GET /api/internal/legal-acceptance/[key]?hash=<64 hex>` reads one founder's decision row through `verify_legal_acceptance`. The ship hold gate (`web-acceptance <key> <hash>`) discharges a hold on a legal text only when the answer is `accepted`, the row check passes, the hash equals the committed text, the text has not expired (`valid_until`), and the hold's own `Hold:` line names the text's key as a whole token. The binding to the key is lexical; its residual is accepted in the ADR-319 PR-D amendment. This purpose is not new in kind: it is the reason the record exists (accountability for a decision on a named text), applied at the moment the text is relied on. Same person and same decision, but the use adds a table and a possible appearance in an agent session (items 2 and 3), so I treat it as compatible under Art. 6(4) because of the link to the original purpose, the operator-first context, the absence of any effect on the founder, and the safeguards below.
2. *A third table*, `legal_acceptance_ack` (acceptance id and acknowledgement time). It is pseudonymous personal data, not data that is non-personal on its own: its key is the id of a `legal_acceptance` row that Jikigai holds, so Jikigai can link it to the founder id with one join. It is excluded from the self-serve export and served on request, like the other two. It is written for every user who records a decision (the decide path acknowledges every recorded row, and the `approval-queue` flag is global), not only for the operator: "operator first" is a roll-out commitment, not a limit in the code.
3. *The answer can appear in an agent session.* The gate prints a verdict that can name the status (for example that the founder declined), and that output can enter an agent session on the operator's machine. The four fields (status, text hash, decision time, checksum flag) about the single configured founder can therefore appear there. The note never does. I do not decide here whether that session is within a processing activity, and I do not call any provider a processor for it: the register treats the user's own Claude Code installation as out of scope, PA-34 (operator-assisted runs) is the nearest activity, and the Anthropic DPA snapshot lists processor roles only for PA-22, 27, 31, 32, 33 and 34 with its zero-retention amendment unsigned. It is a counsel question (Register Maintenance item 17(h)); PA-40 (b) and (d) are marked accordingly.
4. *The note is read by pull only*, by the operator personally. It is not readable through the endpoint or any `service_role` path. A database-owner credential could read it; that credential is held by the operator and by the production migration pipeline (a CI secret), and no agent session is meant to use either, which is a rule and not a control.

**Balancing, re-run.**

- (i) Interests: unchanged.
- (ii) Data and subject: the operator is the only founder expected; one more table of an id and a time, written for every recorded decision.
- (iii) Expectations: the operator is the controller's principal and chose the gate. For any other founder the expectation gap is wider, because a Jikigai tool would read their decision to decide whether Jikigai ships. That is not assessed here.

- (v) Safeguards: bearer-gated; exactly four fields; founder id taken from configuration only, never from the request; hash answered from the database; 503 until configured; pull-driven; no push.

**Outcome (draft, provisional): unchanged.** Legitimate interest prevails for the operator-first stage, subject to the retention proposal and the counsel items above.
