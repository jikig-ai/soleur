# security: complete the #11294 log-exposure audit tail and build the #11711 per-secret rotation census

## Overview

Complete the agent-side remainder of the `random_id` log-exposure arc (issues #11294 and #11711). Redaction of Terraform `random_*` id output from every plan/apply stream and public sink merged via #11551, #11674 and #11930; the owner-run dispatch-only rotation routes merged via #11918 (`key-rotate.yml` / `scripts/key-rotate.sh`, seven keys) and #11287 (`inngest-key-rotate.yml`, dedicated Inngest pair, ADR-307). What remains is documentation-class: (a) a per-job audit verdict recording whether `[id=...]` lines for the Inngest key addresses reached a retained public log, through which sink, and under which retention window; (b) a per-secret census with one row per `random_id`/`random_password` resource, its rotation route and readiness state; (c) readiness notes per secret for the owner-run `key-rotate.yml` / `inngest-key-rotate.yml` dispatches; (d) issue comments on #11294 and #11711 reporting the agent-side results. Every rotation, deletion and production-mutating act is owner-gated and recorded as an Operator Hold, never a work item.

## Problem Statement / Motivation

`hashicorp/random`'s `random_id` has an `id` that is the base64url of the generated bytes, and Terraform prints it on every create, destroy and refresh line. The Inngest signing/event keys are `random_id` resources and this repository is public, so every workflow run that streamed a Terraform plan/apply refresh before the redaction merged published key material into a retained public log (and, for the drift workflow, into public `infra-drift` issue bodies/comments). The evidence-preservation record (`knowledge-base/legal/audits/2026-10-31-11294-run-log-evidence-preservation.md`) enumerated and deleted the hit runs and redacted the comment/body surfaces, and the CLO determination (`knowledge-base/legal/audits/2026-10-29-clo-determination-11294-random-id-log-exposure-art-4-12.md`) holds the breach posture. Two gaps remain agent-side:

1. **The audit tail.** #11294 asks for a per-job verdict: for every workflow job whose plan or apply can reach `random_id.inngest_{signing,event}_key_{prd,dev,dedicated}` and prints Terraform output, did `[id=...]` lines for those addresses reach a retained public log, and what is the retention window? The record gives per-job hit counts but not the per-job mechanism/verdict write-up, and it leaves one unexplained signal (89 `drift-check` job-row hits despite the drift plan being captured in a command substitution since file creation).
2. **The rotation census.** #11711 asks for one row per exposed secret — dedicated Inngest signing+event pair (route #11287, gated on the #11215 soak), the census `random_id`/`random_password` resources, `random_id.tunnel_secret` last+separate (roll-forward only), and the inngest-host pair (needs its own rotation ruling) — plus per-secret readiness notes for the owner-run workflows.

The CLO re-assessment trigger is **2026-11-08**: if rotation is not recorded complete in #11294 by then, the CLO re-assesses. Agent-side completeness (verified census + readiness notes) is what the owner needs to dispatch efficiently inside that window.

Spec lacks valid `lane:` — defaulted to cross-domain (TR2 fail-closed).

## Technical Considerations

### The refresh mechanism (why every job printed every key)

`terraform plan -target=X` and `terraform apply` refresh the **whole state**, not the target set — the target only filters the diff. Every job on the `apps/web-platform/infra` root that streamed `terraform plan`/`apply` therefore printed `random_id.<name>: Refreshing state... [id=<base64url key>]` for **all twelve** `random_id` resources in state (the six Inngest key resources, `inngest_manual_trigger_secret_{prd,dev}`, `kb_drift_ingest_signing_key`, `egress_audit_ingest_token`, `github_webhook_secret`, `tunnel_secret`) on every run, regardless of its `-target` list. This is the mechanism sentence the per-job verdict table hangs on.

### The drift-check anomaly (audit tail's live question)

The census recorded **89 `drift-check (apps/web-platform/infra)` job-row hits** in run logs, yet the drift plan has been captured in `PLAN_OUTPUT=$(terraform plan ...)` since the file's creation commit (`e997bc5185`) — refresh lines never reach its step log. Candidate attributions for the work phase, in order: (a) the census's `id_lines`/`random_addr_lines` columns counted non-key value-shaped lines from a step other than the plan (the TSV `secret_shaped_random_id_lines` column discriminates — it lives in the operator's scratch area, not committed); (b) a step in a since-changed revision echoed plan content (git-history scan of `scheduled-terraform-drift.yml` over the census window 2026-07-31→10-29); (c) the `infra/github` or `sentry` matrix legs' output attributed to the wrong job row. Resolution is recorded either way; all hit logs are deleted, so the finding is mechanism-attribution, not live exposure.

### Retention windows (verified)

- **Run logs:** GitHub default 90 days; for public repositories configurable only 1–90 days (docs.github.com "Configuring the retention period…"; confirmed by the census's own "oldest runs have expired logs" gap and HTTP-410 semantics). Measured live 2026-10-29: `days: 90`, `maximum_allowed_days: 90` via the repo artifact-and-log-retention endpoint.
- **Artifacts:** per-upload `retention-days` — rehearsal evidence 90d, infra-validation suite logs 14d, registry artifact pin 7d (`registry_pull_path_gate`), cf-lb continuity default.
- **Issue/PR bodies and comments:** indefinite until edited/deleted; **edit history remains publicly readable** on edited-in-place items (74 bodies + 234 comments) — the unremovable residual.
- **Census TSV:** `census-11294.tsv` (1448 rows, sha256 `6ba16467…`) lives in the operator's scratch area, uncommitted.

### Provider facts (verified against hashicorp/random source)

- `random_id.id` = base64url of the bytes — the key material (issue premise, confirmed).
- `random_password.id` = literal `"none"` (`resource_password.go`: `plan.ID = types.StringValue("none")`); `result` is sensitive and prints `(sensitive value)` — random_password resources are **not exposed via `[id=]` or plan-block output**. `random_string` id **is** the value — no `random_string` resources exist (verified by census grep).
- `random_id.tunnel_secret`: `terraform -replace` is a no-op on the live tunnel (`tunnel.tf:14` feeds `cloudflare_zero_trust_tunnel_cloudflared.web.secret` under `ignore_changes = [secret, config_src]` at `:21`; the original value is irrecoverable per `:16-17`). A real rotation replaces the tunnel and rebuilds web-2 — roll-forward only (ADR-307 amendment of 2026-10-29).

## User-Brand Impact

- **If this lands broken, the user experiences:** no direct artifact — the failure mode is a *wrong census row*: a secret believed unexposed (or believed rotated) stays live while a reader of the deleted logs holds it, and the forged-event channel into user Inngest workloads stays open.
- **If this leaks, the user's workflow is exposed via:** a census or audit artifact that itself carries a key value, or a per-job verdict that under-reports a sink (e.g. marks the drift issue stream "not a log" and drops it). The artifacts must contain addresses, dates, counts and verdicts only — never a value.
- **Brand-survival threshold:** `aggregate pattern` — the exposed items are shared-channel auth keys; a leak harms the channel every user shares rather than one user's records. Recorded as a challengeable decision row.
- **Threshold decision (challengeable):** the CLO already adjudicated the underlying incident under Art. 4(12) as a failed Art. 32 measure with no evidence any key was read; this plan adds documentation, not a new exposure, so no per-PR CPO sign-off — but a mis-attribution that hides a live secret is the harm the threshold names.
