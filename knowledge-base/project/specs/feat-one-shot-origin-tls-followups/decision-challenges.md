# Decision Challenges — feat-one-shot-origin-tls-followups

| Item | Class | Ruling |
|------|-------|--------|
| Sentry alert for `feature:origin_tls`: one any-event rule vs a broad rule plus a tight `phase:runtime` / `reason:unexpected-close` rule vs a runtime-only rule; whether `cert_expiry` pages | technical | Ruled by CTO agent, 2026-11-08: one `sentry_alert` rule matching `tagged_event feature eq origin_tls` with no `op` filter, `frequency_minutes = 47` (re-check against `origin/main` at work time), triggers first_seen + reappeared + regression + `event_frequency_count {1h, 0}`, email `issue_owners` with `ActiveMembers` fallthrough, `cert_expiry` pages, no second rule - a dead :443 under strict is a 52x outage for every user and a startup `load`/`create` rejection means rotation or config is broken before the next restart; a tighter rule would page the same person by the same route and only add op-contract surface. The mechanism is the repo's existing one (`apps/web-platform/infra/sentry/issue-alerts.tf` + `alert-reference.json` + an op-contract test), so no new ADR, only an ADR-321 item-11 sentence. |
| Plain :80 server slow-header cutoff (300 s inherited from Node `requestTimeout`; the 910 s `headersTimeout` assignment is dead): leave, set `headersTimeout` only, lower `requestTimeout`, or pin both | technical | Ruled by CTO agent, 2026-11-08: set `headersTimeout = 60_000` and pin `requestTimeout = 300_000` explicitly on the :80 server only, through a new import-safe module `apps/web-platform/server/http-timeouts.ts` (`applyPlainHttpTimeouts(server, t?)`, throws when headers > request) - 60 s matches the :443 listener and removes a 5x looser slow-header exposure on a port that stays open until the bake passes; `requestTimeout` stays 300 s because it bounds whole requests (uploads, KB posts) and nobody has shown a need to lower it; idle keep-alive is unaffected (measured: a small `headersTimeout` did not close an idle socket, `keepAliveTimeout` stays 905 s). The :443 server and its R-A test pins are untouched. |
| Cheap in-app `/health` timing marker (monitored stdout `SOLEUR_*` line) in this PR | technical | Ruled by CTO agent, 2026-11-08: no, defer - a handler-side marker cannot see TLS handshake or connection-setup cost (they happen before the handler runs), `/health` awaits `checkSupabase()` on every request so the app-side tail is most likely the Supabase leg, and `/health` p90 is not user-facing latency; it would put new code in the paging and deploy-gate path of an otherwise config-only merge. The runbook carries a zero-code isolation (a Supabase-free same-origin path as control, then the Cloudflare analytics query once `CF_API_TOKEN_ANALYTICS_READ` exists) and the triggers that would revive the marker (control path also regresses by more than 50 ms at p90, or a step change in the CF origin duration aligned with the flip, or a user-facing latency complaint). |
| Scope of the CI download hardening: seven gitleaks copies, the same-class actionlint copy, the crane downloads in the production-apply workflow, a shared helper, extra curl flags | technical | Ruled by CTO agent, 2026-11-08: harden all seven gitleaks copies plus the actionlint copy (same CDN, same file, one-line change) with exactly `--fail --retry 5 --retry-all-errors`; crane and the rest of the release-download class are out of this PR and get one tracking issue filed in the work phase; no shared helper or composite action (YAGNI, shapes differ, `secret-scan.yml` is a required check); no `--retry-delay`/`--max-time` (default backoff is about 31 s, which rides out blips and not an 80-minute outage, so the PR text must not claim otherwise); the test extends Test 5 of `plugins/soleur/test/required-checks-canonical-parity.test.sh` by scanning rather than hand-listing, with floors, scoped to the gitleaks and actionlint URLs so the crane sites do not turn it red. |
| REQUIRED-mode fatal paths in `origin-tls.ts` call `exit(1)` with no Sentry flush, so the new alert can miss the unexpected-close and startup-fatal events it exists for (found in plan review): fold a fix into this PR, document it as a carried risk, or flush inside `reportSilentFallback` | technical | Ruled by CTO agent, 2026-11-08: fold a bounded `exitAfterFlush` into the default `exit` in this PR (`EXIT_FLUSH_MS = 2_000`, hard timer +250 ms, always exits on resolve/reject/throw/hang, idempotent, `params.exit` injection unchanged, `Sentry.flush` not `close`) - the rule exists to page on exactly these two exit paths and `reportSilentFallback` only queues the event; the pino error mirror is itself mirrored to Sentry so it does not rescue the page (Vector error-level forwarding unverified); the change runs only on a dying process, is about 12 lines plus six tests, reuses the 2 s bound of `crash-handlers.ts`, and touches no timeout. Rejected: documenting the gap (ships a known hole in the rule's main purpose), flushing inside the shared reporter (40+ call sites), `Sentry.close` (disables the SDK, order-dependent tests). Fallback if the owner objects: document it and file a tracking issue. |
