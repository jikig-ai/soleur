# Decision challenges — feat-one-shot-sentry-iac-token-rotation

Plan: `knowledge-base/project/plans/2026-11-13-feat-sentry-iac-token-rotation-profile-plan.md`.
The measurements behind these rulings were taken 2026-11-13. They recorded only HTTP status codes,
sha256 digest equality and secret names. No token value was printed or stored.

## Decision Classes

| Item | Class | Ruling |
|---|---|---|
| 1. Token for postmerge issue/event reads. The brief says "Make issue/event reads use SENTRY_IAC_AUTH_TOKEN", which diverges from this ruling, so it is surfaced to the operator. | technical | Ruled by CTO agent, 2026-11-13: keep the `SENTRY_ISSUE_RO_TOKEN` → `SENTRY_ISSUE_RW_TOKEN` (GET-only) ladder. Fix the stale prose instead: the graceful-degradation rows, the Production Debugging bullet (name RO first, with `SENTRY_IAC_AUTH_TOKEN` as the last-resort read, which goes in the reference because of the SKILL.md byte budget), and the dead `jikigai` fallback. - The RO token already returns 200 on both the single-issue read and the org issue search, with scopes `[event:read, org:read]`. `SENTRY_IAC_AUTH_TOKEN` carries `project:admin` and `alerts:write` (#8681), and the reference forbids widening this GET. Dissent: if the operator wants IAC for reasons other than reads working, that is a scope call. |
| 2. Doppler `prd_terraform` store | technical | Ruled by CTO agent, 2026-11-13: write Doppler `prd` and `prd_terraform` unconditionally and read each back by digest. Do not write the other `prd_*` carriers. Report them as `STALE COPIES (no known reader in repo)`, derived from the live enumeration, without blocking the revoke. File one follow-up to remove them (#12740, filed). - A Doppler branch config either inherits the root's value or holds its own copy (the planning-time claim "independent copies, not inherited" was corrected in review), so a root-only write is not proven to reach `prd_terraform`; it is written explicitly. After the store, the other carriers are classified by digest as `follow soleur/prd` (now new) or `own copy` (not the new value), replacing the planned `STALE COPIES` label. Blocking on the other copies would stop every rotation from completing. Writing all 8 would put a live admin token into configs no code reads, some of which are injected whole into hosts. Dissent (DHH, code-simplicity): fail on an override, or rely on inheritance. Both were rejected on the measurement. A reader outside the repo would argue for writing that one named config. |
| 3. Probe hosts for the `iac` profile | technical | Ruled by CTO agent, 2026-11-13: probe only the org subdomain (`jikigai-eu.sentry.io`). No control-host `regionUrl` read and no region pin; `ro` keeps its own. - Every IaC consumer uses the org subdomain: the terraform provider `base_url`, `sentry-alert-live-fidelity.sh`, `sentry-monitors-audit.sh` and the `sentry-audit-gate.yml` host pin. |
| 3b. `iac` probe set size | technical | Ruled by CTO agent, 2026-11-13: four probes (project read, `workflows/`, `monitors/`, org issues search). Cut the planned org-detail, `detectors/` and `releases/` probes. - Exact `.auth.scopes` equality already proves the permissions. Each of the four stands for one consumer class, and the other three add no evidence on the same host. |
| 4. Dry-run Doppler proof (the CLI has no no-store flag) | technical | Ruled by CTO agent, 2026-11-13: the header and the test state that the CLI cannot prove the store form without writing. The test pins the exact argv and stdin through a stub. The dry run and the live run share the read-only Doppler preflight before capture. - A Doppler login failure surfaces before the GitHub secret holds the new token. |
| 5. Test (none existed, though the brief says "extend the existing test") | technical | Ruled by CTO agent, 2026-11-13: create `scripts/rotate-sentry-actions-ro-token.test.sh`, registered via `run_suite`, in two commits. Commit 1 characterises `ro` against the unchanged script; commit 2 adds `--profile` and the `iac` rows. Stubs record argv and stdin to files and never echo values. - Commit 1 is the proof that the refactor left `ro` unchanged. |
| 6. Store order and partial-failure message | technical | Ruled by CTO agent, 2026-11-13: order is GitHub repo secret, Doppler `prd`, Doppler `prd_terraform`, with the Doppler preflight before any write. If the first target fails, print "revoke the NEW token". On a later failure, print the target lists and "do NOT revoke the old token yet — re-run the rotation, then revoke both". - The script shreds the token, so a full re-run is the only repeatable path. |
| 6b. Doppler copies through a `doppler_secret` Terraform resource vs the script's verified stdin store (Phase 2.8 IaC routing gate) | technical | Ruled by CTO agent, 2026-11-13: ratified the terraform-architect ruling SCRIPT-STORE-IS-CORRECT. - Terraform cannot mint the token, which is issued in-page. A resource fed by a TF var would put an admin token in plaintext state, skip the scope and probe gate, and make the Sentry root manage its own credential. |
| 8. Preflight shape and `dig_of` read failures | technical | Ruled by CTO agent, 2026-11-13: one `doppler configs -p soleur --json` enumeration before capture replaces the two `configs get` calls. It asserts that `prd` is the root, that `prd_terraform` is a `prd` branch, and that there is at least one branch, and it builds the target and stale-copy lists. `dig_of` treats a non-zero rc or an empty value as a read failure (UNVERIFIED, never a match, never a write trigger). - A failed get otherwise hashes the empty string and is compared as data. |
| 9. Partial-state report lists | technical | Ruled by CTO agent, 2026-11-13: three lists, HOLD NEW / UNVERIFIED (value unknown) / STILL HOLD OLD. A `gh secret list` failure after a write is reported as "GitHub possibly holds new". The revoke-old guidance prints only when all three targets are in HOLD NEW. - The earlier draft misreported a written-but-unreadable target as holding the old value. |
| 10. Prove-then-revoke gate in the runbook | technical | Ruled by CTO agent, 2026-11-13: after the script reports all three targets in HOLD NEW, dispatch `scheduled-sentry-alert-drift.yml` and `scheduled-terraform-drift.yml` and watch each by run id. Revoke only when each run's log shows a POSITIVE verdict line and no rendered `##[error]` auth/secret line (superseded twice in review: the plan output never reaches the log, so a 401 search proved nothing, and bare error strings matched the echoed step source on every run). A non-Sentry red does not block. - Terraform-drift is plan-only, and its exit 2 means drift, not an auth failure. |
