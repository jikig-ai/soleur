# `approval-queue` flag: creation hand-over (not done by the PR)

The PR registers the flag in code only (`lib/feature-flags/server.ts` RUNTIME_FLAGS, `.env.example` `FLAG_APPROVAL_QUEUE=0`, `flip.sh` map). Nothing is created in Flagsmith or Doppler and nothing is flipped. Absent means OFF, so the merge does not depend on it.

## Operator steps (typed-yes, each a production write; run only after the legal commit and the post-merge checks below are green)

1. Create the feature with `soleur:flag-create` (name `approval-queue`, default OFF, mirror `FLAG_APPROVAL_QUEUE=0` in Doppler dev and prd).
2. Do NOT flip it as part of the create. Enabling is a separate decision per workspace cohort via a per-workspace segment override (`soleur:flag-set-role`), evaluated per workspace identity.

## Enabling gates: ADR-309 flip checklist (copied verbatim; the ADR is the source, edit both together)

Authoritative: `knowledge-base/engineering/architecture/decisions/ADR-309-durable-action-bound-approval-requests.md`, section "Flag-flip checklist (before the flag is turned on for anyone)". "Below" and "above" in the copied text refer to the ADR sections of that name (Accepted deviation, Rollback and post-deploy verification). Nothing in this PR flips or creates the flag.

1. **Cohort rule: no workspace with more than one member gets the flag until the Owner card names the requester and `reattach` stops sending full action text to non-Owners.** Until both hold, the flag is limited to
   single-member workspaces (also: the decide path out of the agent process, or the sentinel gap re-accepted). Check the `workspace_members` count for the workspace before any per-workspace override, and **re-check it on
   every member invite**: inviting a second member to an enabled workspace takes it out of the cohort, so its override is removed first or in the same change.
2. **`SENTRY_USERID_PEPPER` is non-empty in the running container** (not only set in Doppler `prd`; invariant 1 fails closed without it, and `approval-key-unavailable` pages). Verify read-only after the deploy that
   the container has it and that the `approval-key-unavailable` alert has no events. **Never rotate the pepper while any approval is live**: a rotation invalidates every pending and approved row (and changes ADR-029 pseudonyms).
3. **Route the cron monitor** (accepted deviation, below): `scheduled_approval_expiry` is declared-unrouted under the two-PR rule and has no independent cover (the unanswered alert is emitted by the sweep itself, and no Better Stack
   missing-`SOLEUR_APPROVAL_SWEEP` monitor exists). After its first measured check-in, route it into `cron_monitor_failure` (add its id to the sorted `monitor_ids`, delete the unrouted entry) in a follow-up PR before the flip.
4. **Real-SDK probe and post-deploy verification**: re-run the probe (`dev-probe-approval-gate.ts`, ADR-305 checklist) and confirm the post-deploy verification below is green.
5. **Erasure and fingerprint conformance** (compliance-posture row, item (i)): after a real-database erasure of a personal workspace, `select count(*) from approval_request where workspace_id = :erased_user_id` is 0 and the
   fingerprint is keyed (pepper set, known-answer vector green); both recorded in `knowledge-base/legal/audits/`. The integration test `approval-request.tenant-isolation.test.ts` is the falsifier; `verify/180` deliberately has no row-level check (invariant 3).
6. **CLO attestation and sign-offs** (compliance-posture row, items (b), (h), (i)): (b) the full CLO attestation is discharged in `knowledge-base/legal/audits/` (a Jikigai-owned canary needs only its (b-canary) verification step);
   (h) the autonomous-mode card copy is non-provisional with both the CPO and CLO reviewer fields filled; (i) as item 5. Evidence gates #9776 and #10111 are closed.
7. **First-call flag-error posture**: decide whether to harden a flag read error on the first gated call of a turn to deny before enabling beyond the Jikigai canary (today it takes the flag-off path, a legacy card; see "Fail closed, sticky for the rest of the turn").
8. **Copy and compliance for the cc push tool** (Ref #11636, see the 2026-11-05 #11636 addendum): before the flag is on for anyone, (a) reword the web-egress toggle copy first: it says agents "can't push to git remotes", which stops being accurate once `github_push_branch` is registered in the Concierge (sweep `git grep -n "push to git remotes" -- apps/web-platform`; today that finds the two strings in `components/settings/web-egress-toggle.tsx` and one in the scope-grants settings page); the accurate claim is that sandboxed commands cannot push while the egress forwarder is live (item 12), while an agent can propose a push of the approved commit that runs only after an Owner approves it; (b) the CLO check and a compliance-posture addendum for the new action type, including the PA-38 `canonical_action` wording check (item 10 cross-references this); (c) confirm the approval card and the notification name the commit, repository and branch (the card rows are `REPOSITORY`, `BRANCH`, `COMMIT` and `FORCE PUSH` in `server/approval/render.ts`; push and email stay content-free). That holds today, so as a bare "names it" check it is weak: the card shows an opaque commit sha, while the push publishes the commit's whole unpushed ancestry (every ancestor not yet on the remote, workflow-file edits under `.github/workflows` included, and anything a prompt-injected agent committed), none of which the Owner sees. The stricter test is item 11. No code in this PR changes the card; (d) the public-document qualifier "not switched on for any workspace that Jikigai does not own" stays until items 8 through 12 are discharged.
9. **`.git` hook, config and environment exposure on the approved push** (Ref #11636). The approved push runs `git` in the agent-writable workspace, in the dispatch process, outside the sandbox, and git trusts what that directory contains: `.git/hooks/*`, `.git/config` (`core.hooksPath`, `core.sshCommand`, `url.*.insteadOf`, `http.*`), replace refs and `objects/info/alternates`. The legacy path hands that child the FULL server environment (`{ ...process.env, ... }` in `gitWithInstallationAuth`), and a push failure's stderr (path-stripped) is relayed to the model in the tool result. A hook or config entry the agent wrote therefore runs on an Owner-approved push that looks benign (the card shows repository, branch and commit, not hooks), with every secret in the server environment in reach and a channel back to the model, not only the one-hour installation token. This is pre-existing (the legacy runner has it with the flag off, see ADR-309, section "Residual risk: sentinel discipline"); whether the cc sandbox can write `<workspace>/.git` has not been measured by a live probe. **It gates any enablement, the Jikigai canary included, until 9a is merged.**
   - **9a, in this PR's code (cc form only, opt-in `hardened` field; the legacy push is byte-identical), closed for hook execution, config-driven command execution and server-environment exposure; NOT for token diversion (that is 9b):** reuse of the existing `_git-hardening` leaf (`--no-replace-objects`, `core.hooksPath=/dev/null`, `core.fsmonitor=false`, `core.attributesFile=/dev/null`), the unscoped `http.proxy` / `http.extraHeader` and `https://github.com/`-scoped proxy resets (these do not out-rank a more specific `http.<url>.*` key the agent writes), `push.followTags=false`, `GIT_ALLOW_PROTOCOL=https`, a child environment built from an allowlist instead of `process.env`, pins for `GIT_DIR`, `GIT_COMMON_DIR` and `GIT_OBJECT_DIRECTORY`, and a pre-flight `.git` check (real directory, no symlinked or redirecting entries such as `commondir` or `objects/info/alternates`). See the addendum, item 7, for the exact list and the tests.
   - **9b, residual, a flip precondition beyond the Jikigai canary:** the agent-writable `.git/config` can still divert the installation token to another https host or observe it: `url.<base>.insteadOf` and `url.<base>.pushInsteadOf` (the latter applies to a literal push URL), a URL-scoped `http.<url>.proxy` or `http.<url>.extraHeader` (git picks the most specific URL match, which beats the `-c` resets), `http.<url>.sslVerify` / `sslCAInfo` and `http.curloptResolve` (with a proxy or resolver, TLS verification off lets the Basic auth header be read). A `url.<base>.insteadOf` rewrite to an `ext::<command>` URL (with a repo `protocol.ext.allow`) is command execution as the dispatch user; this PR clamps it with `GIT_ALLOW_PROTOCOL=https`, so what remains is https diversion (`core.sshCommand` is moot for an https URL). `commondir` and the other redirect entries are refused and pinned for the known list, but the check is a pre-flight and not atomic with the later git children, so a sandbox process that outlives the tool call can change `.git` after it. The approval gate's own read of `.git` (`gitHeadSha` in `server/approval/gate.ts`, a plain `git rev-parse HEAD` with the inherited environment, in code this PR does not touch) is not hardened. Close it by either (i) a live probe showing the cc sandbox cannot write `.git/config` (and cannot replace `.git`), or (ii) pushing from an isolated, trusted `GIT_DIR` with `GIT_ALTERNATE_OBJECT_DIRECTORIES` so the agent-writable directory is never the git directory. `remote.*.pushurl` is NOT a vector for this push: `pushBranch` pushes to a literal URL, and `pushurl` applies only to a named remote (git documentation; not probed here).
   - The cohort rule in item 1 is a policy control, not a technical one: it limits who is exposed, it does not stop an agent from planting a hook in an enabled workspace. The tracking issue for 9b is filed by `soleur:ship` from the decision-challenges record of this PR.
10. **Register and DPA preconditions for the write tool (CLO, 2026-11-05), before the flag is on for anyone.** The earlier "no Art. 30 trigger" advisory stands for the dark registration only and is withdrawn as to the flip: the Art. 30 register (Processing Activity 9, "cc-soleur-go Router In-Process MCP Tool Surface") conditions Phase 2 promotion of the GitHub tools on per-tool TOMs, a documented balancing test (cited there to #3722, which is the open Phase 2 promotion issue) and a verified GitHub DPA, and the flip is that promotion. No balancing test or per-tool TOMs for the write tool exist in the knowledge base today. (a) Verify GitHub DPA acceptance at GitHub Settings and flip the compliance-posture GitHub Inc row from PENDING to AUTO with evidence; (b) amend PA-9 to cover the write tool: per-tool TOMs (limb g) and a documented Art. 6(1)(f) balancing test (limb b and the lawful-basis cell); (c) the compliance-posture addendum for the new action type (this is item 8(b); cross-reference); (d) check whether the Privacy Policy, Data Protection Disclosure and GDPR Policy sentences on GitHub cover agent-initiated writes (wording remains an operator hold; this PR edits no legal text).
11. **HARD precondition beyond the Jikigai canary: the approval card discloses what the push newly publishes (CLO, 2026-11-05).** An Owner approval that does not disclose what the push newly publishes and where it goes is not an informed controller authorisation (Art. 5(1)(a), 5(2), 25). Before any enablement beyond the canary, the approval card (or a surface reachable from it) must show the commit subject, the author, a diffstat or the changed paths, labelled agent-authored, for the commits the push adds, and the destination; otherwise record a dated controller decision accepting the residual, with its rationale. The canary needs only a recorded operator acknowledgement. This is a stricter form of item 8(c).
12. **Toggle-copy forwarder dependency (CLO and CTO, 2026-11-05).** The reworded toggle copy (item 8(a)) must state that "sandboxed commands cannot push" holds only while the egress forwarder is live, must be accurate in BOTH forwarder states, and must cite the code that shows the dependency: the sandbox web-egress deny census is applied only when `allowWebEgress` is true, and the cc path sets `allowWebEgress: args.webEgress !== undefined` (`server/agent-runner-query-options.ts`, `WEB_EGRESS_ENV_DENY_CENSUS` in `server/agent-runner-sandbox-config.ts`). With the forwarder degraded the quarantine is off, and Bash `git push`, `gh pr create` and `gh workflow run` reach the same GitHub effects with no approval-queue grant (pre-existing, not changed by registration, addendum item 10); the push tool itself does not depend on the forwarder. An absolute no-push statement that fails when the forwarder is degraded is a misleading representation to the Owner. The public qualifier in 8(d) is extended from "8 and 9" to "8 through 12".
