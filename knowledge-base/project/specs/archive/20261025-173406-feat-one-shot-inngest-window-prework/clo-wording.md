## 1. Interpretation of the 2026-10-15 conditions [policy]

- The limb "never in Doppler or anything holding the passphrase" binds the READ-capable token and every copy of the header. The write-only host credential, the bucket name and the endpoint may ride `soleur-inngest/prd` with the passphrase: a credential that can only PUT cannot retrieve the header. A separate Doppler config or service token is NOT required (a new service token is a new key-reading path).
- Write-only must be proven: the minted credential must PUT successfully and get 403 on GET and LIST, recorded by status code only before the credential is written anywhere. Whether R2 can mint a bucket-scoped write-only S3 credential is not established [inherited, unverified]. If it cannot, STOP: a read-write credential must not enter `soleur-inngest/prd`.
- No standing read-capable credential anywhere (Doppler, tfstate, GitHub secrets, CI). The owner mints one at recovery and revokes it afterwards.
- Do not copy the web-class precedent (credential pair beside its passphrase, an accepted ADR-263 residual) with a read-capable credential.
- Accepted residuals for a write-only credential: anyone who can read it (host, `inngest-boot`, the arm token, `DOPPLER_TOKEN_TF`) can overwrite or poison the single copy (integrity and availability, not confidentiality; R2 has no versioning); the Terraform R2 token can manage or delete the bucket and its reach to read objects is NOT established.
- The real hazard is a stale copy: a superseded header keeps old keyslots, so "retain only the current header" is the load-bearing condition.
- "EU" was shorthand for the narrowest placement control available, never a residency claim. Preferred: R2 jurisdiction `eu` (storage-location guarantee, not a change of custodian). Measured 2026-10-24: pinned provider cloudflare 4.52.7 `cloudflare_r2_bucket` has no jurisdiction attribute. Route (ii) is permitted: ship on `location = "WEUR"` with the sibling files' Chapter V wording verbatim, and never write "EU" for a `default`-jurisdiction bucket in any record, comment or ledger cell. A jurisdiction bucket uses a different S3 endpoint (`<acct>.eu.r2.cloudflarestorage.com`) [inherited, unverified].

## 3. PA-13 (g) new item (15) - appended after (14)

> (15) **Off-host backup of the LUKS header only (declared #9927 item 1; ADR-282 addendum; GATED OFF: no copy exists until the first recorded successful upload).** Provides: a recovery path for ONE failure mode, corruption or overwrite of the LUKS header region of `hcloud_volume.inngest_redis_luks` while the volume and the passphrase are intact (`cryptsetup luksHeaderRestore` from the current copy). Does NOT provide: **Art. 32(1)(c), the ability to restore availability and access to personal data after an incident, is still NOT provided: accepted residual.** The AOF ciphertext has no off-host copy (ciphertext backup is parked, #9927 item 1b), so loss of the sole volume, or of both passphrase copies, still destroys the data. Design limits: the copy holds keyslots encrypted under the passphrase and not the passphrase; the host holds a WRITE-ONLY credential delivered with the passphrase's Doppler project (it cannot retrieve the header); no read-capable credential is stored anywhere (the owner mints one at recovery and revokes it after); the bucket is distinct from the Terraform state bucket and from both workspaces header buckets. Does not defend against: anyone who can read the write-only credential overwriting the copy (integrity, unversioned bucket); a holder of the Terraform R2 token deleting the bucket (reach to read objects not established); a stale copy during the window between a key change and the next upload; the transfer position in (e) and the open classification #7671. Retention: current header only, one fixed object key overwritten on every upload (re-taken after every key change), no versioning, deleted at volume decommission by the owner under the runbook; no per-subject erasure path because the header is not per-subject. Policy, not a measurement; no object has been uploaded.

Also add a conditional Superseded marker under the (13) sentence "the ciphertext and the LUKS header have no backup (escrow was rejected on confidentiality grounds, ADR-142)": true until activation.

## 7. Retention and erasure statements (runbook text)

1. Only the current header is retained, at one fixed object key. Each upload overwrites it; the bucket has no versioning.
2. The keeper re-takes after every key change. The runbook step for any key change gates on that re-take, and the daily run bounds the stale window.
3. The overwrite is the purge, performed by the host's write-only credential on each upload.
4. At volume decommission the owner deletes the object first, with an owner-minted credential, and records the deletion in the runbook. The volume is not retired or unprotected until that is done.
5. The bucket keeps `prevent_destroy`, so the object, not the bucket, is what is deleted.
6. There is no per-subject erasure path (the header is not per-subject). No crypto-erasure is claimed.
