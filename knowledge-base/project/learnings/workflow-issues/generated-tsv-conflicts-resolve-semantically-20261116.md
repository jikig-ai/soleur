# Resolving a CONFLICTING PR whose generated manifests raced main (#12698)

## Problem

PR #12698 went `mergeable: CONFLICTING` after main moved: four conflicts, two of
them generated manifests (`scripts/suite-durations.tsv`,
`scripts/suite-shard-legs.tsv`). The branch side had *fully regenerated* both
tables from five measured CI runs (re-pricing every row, `default-weight-ms=1800`);
main had made *incremental additions* (two new suite rows). A textual
three-way merge produces a 290-line conflict hunk that cannot be resolved by
eyeballing, and `scripts/resolve-regenerable-conflicts.sh` refused — it only
recognizes LikeC4-generated artifacts.

## Symptoms

- `gh pr view` shows `mergeable: CONFLICTING`, `mergeStateStatus: DIRTY` while
  every check is green — green checks on a conflicting head are not evidence
  the `pull_request` workflows ran the merged code.
- `git merge origin/main` stops on the two TSVs plus two shell scripts whose
  conflict is arithmetic, not text (both sides bumped the always-on floor for
  different reasons).

## What Didn't Work

**Attempted Solution 1:** run `scripts/resolve-regenerable-conflicts.sh` on the
TSVs.

- **Why it failed:** the resolver's registry only covers LikeC4-generated
  files; the suite manifests are regenerated by a different tool
  (`regenerate-shard-manifest.py`) and are not in its vocabulary.

**Attempted Solution 2:** hand-merge the durations conflict hunk.

- **Why it failed:** the conflict is one 290-row hunk — HEAD re-measured every
  row while main appended. Picking `ours` silently drops main's two new suites;
  picking `theirs` discards the fresh five-run repricing that is the point of
  the branch.

## Solution

Resolve each conflicted file by *class of change*, not by hunk:

1. **Arithmetic conflicts in shell scripts** (`test-all.sh` floor pin,
   `test-all-affected.test.sh` expectation): derive the merged value, don't
   pick a side. Main added `+1` always-on (#12494 → count 120, floor 115); the
   branch withdrew `-1` (#11556 → count 118, floor 114). Merged count is
   `119`, so floor `114` still satisfies `count - floor <= 5`. Keep **both**
   change comments, pin `_MIN_ALWAYS_ON_DECLARED=114`, and fix the
   auto-merged `want 115` message to `want 114` — the comment/messages are
   half the conflict and merge cleanly wrong.
2. **Generated-manifest conflicts:** take the *fully regenerated* side
   wholesale, then re-derive the other side's additions with the generator's
   incremental mode — `python3 scripts/regenerate-shard-manifest.py
   --incremental --write` pins incumbent rows and places newly-registered
   suites on the least-loaded leg at floor pricing, no CI fetch needed. This
   preserved HEAD's repricing *and* main's two new rows (landed on leg 6,
   weight 6) with zero manual row edits.
3. Re-run every consumer suite of the resolved files before pushing
   (weight-drift, fast-tier-budget, leg-balance, shard-totality, and the
   f1 block of test-all-affected via `--rows 32-32` rather than the ~35-min
   full shard).

## Why This Works

The generator's incremental mode *is* the semantic merge for these files: it
recomputes placement from the durations table, so whichever side's rows are
new get correct legs without trusting either blob's stale assignments for
them. The floor-pin class generalizes too — when both sides move a derived
constant for different reasons, recompute the derivation on the merged
registration set and record both attributions in the comment.

## Review-harness sentinel fallbacks fabricate credit

The same PR's fix rounds surfaced a reusable defect class in grading harnesses:

- `expected_rc()` maintained a hand-copy of the row→rc map; a `row()` added
  but forgotten in the table made *every* mutant grade against a sentinel `9`
  — and since real probe exit codes are only 0/1/2/3/78, `got != 9` always,
  silently crediting the mutant as caught. Fold the map into the row
  declaration site (`WANT[$name]=$want` inside `row()`) so there is one write.
- The *symmetric* hole survives a single-table fold: a **typo'd** row id in a
  mutant/harness list also resolves to the sentinel and over-credits. Close it
  by failing loudly on unregistered ids (`[ -z "${WANT[$r]+x}" ] && fail`),
  not by another lookup table.
- A newly added code path (a `.jobs` body-shape guard) whose deletion leaves
  the suite green is **unpinned** — the fixture needs a case where removing
  the path changes the verdict class (`{"jobs":{}}` → FAIL without the guard
  vs CANNOT ESTABLISH with it), plus a mutant deleting the guard to prove the
  row catches it.
- Slack counters (`_FLOOR=24` vs 28 actual, `-ge 7` vs 8 mutants) re-drift on
  every row add; pin them `-eq` at the actual count so a row addition forces a
  deliberate counter bump.

## Prevention

- For generated files in conflict: check whether the repo has a generator
  `--incremental` mode before hand-editing — it is the merge algorithm the
  manifest understands.
- For derived constants in conflict: recompute on the merged set; never pick a
  side's comment, keep both attributions.
- For grading harnesses: every "expected" value should have exactly one write
  site, and every consumed key should fail loudly when unregistered — a
  sentinel default that any real output differs from is a silent-credit path.
- New fail-closed guards need a fixture that distinguishes their verdict class
  AND a mutant that deletes them, or the harness cannot prove they matter.

## Session Errors

**Resume brief carried stale live-state claims** (head SHA, auto-merge armed,
blocking check) — all three had changed since the brief was written.

- **Recovery:** `gh pr view --json` + check rollup before acting on any brief
  claim; the live query showed DIRTY/CONFLICTING instead of the claimed
  blocker.
- **Prevention:** resume prompts should carry observation timestamps; the
  reader-side gate (query live state before asserting GitHub status) already
  caught this — keep treating briefs as hints, not state.

**`resolve-regenerable-conflicts.sh` attempted on the TSVs** — wrong tool.

- **Recovery:** read the script's registry, found it LikeC4-only, pivoted to
  incremental regeneration.
- **Prevention:** check a helper's coverage list before invoking on a new file
  class; generated ≠ automatically resolvable-by-that-tool.

**`/tmp` copy of the test suite broke REPO_ROOT** — suites derive the repo root
from `BASH_SOURCE`, so a copied file resolves `//scripts/...` and every fixture
row fails.

- **Recovery:** ran the scratch copy as a same-directory sibling (`.verify-*`
  in `scripts/followthroughs/`).
- **Prevention:** never copy a suite out-of-tree for a mutation probe; copy it
  beside the original so `cd dirname/../..` still resolves, and delete after.

**`fix-round-seats.sh --files` usage error** — space-separated list rejected;
the flag takes a comma/newline list.

- **Recovery:** `--help`, reran with commas.
- **Prevention:** read `--help` on first invocation of a gate script rather
  than guessing the list syntax.

**Assertion-floor miscount** — set `_FLOOR=28`, had to bump to 29 after adding
a row (then 30 in fix round 2).

- **Recovery:** suite's own printed count surfaced the drift immediately.
- **Prevention:** after touching assertion-bearing rows, derive the floor from
  the suite's printed total, not from memory of the pre-edit count.

**Forwarded from session-state.md (prior pipeline phases):** invalid
`mechanical` decision-challenge class (reclassed `taste` in-subagent); a
`gh issue view --jq` number/string concat error (fixed in-subagent); four
`pending - assumed` technical rows in decision-challenges.md (resolved by the
batched CTO ruling spawn).

- **Recovery:** all three handled inside their originating subagents / the
  technical-ruling gate before reaching this phase.
- **Prevention:** none additional — the forwarded-errors section did its job.
