# Learning: exact-match bulk redirects need the bare shape too

## Problem

#3328 migrates 23 date-prefixed blog slugs off HTTP-200 meta-refresh stubs
(generated by `plugins/soleur/docs/blog/redirects.njk` + `_data/blogRedirects.js`)
onto Cloudflare Bulk Redirects in `apps/web-platform/infra/seo-bulk-redirects.tf`
(PR-A of a two-merge sequence; the stubs delete in PR-B). The first
implementation emitted two source shapes per slug — `soleur.ai/blog/<date-slug>/`
and `soleur.ai/blog/<date-slug>/index.html` — matching the shapes the stub
generator itself produces. A 4-seat review panel flagged the gap: Bulk Redirects
match `http.request.full_uri` **exactly**, so the bare no-slash form
`soleur.ai/blog/<date-slug>` was uncovered. Today the origin's trailing-slash
redirect papers over it; the day PR-B deletes the stub tree, that form 404s —
a regression inside the exact URL class the migration exists to fix.

## Solution

Emit three source shapes per mapping — `/`, `/index.html`, and bare — in the
`blog_redirect_items` flatten, and add the same third explicit item for the
pre-existing `what-is-company-as-a-service` reslug (69 generated + 13 explicit
= 82 list items). Verified structurally: 23 dated `docs/blog/*.md` files = 23
map entries, each target = the Eleventy date-stripped `fileSlug`; canonicalizer
41/41, mutation 28/28, ssl-mitigation 10/10, `terraform validate` + `fmt`
clean. Post-apply gate (task 1.4) curls all 82 sources for `301` + `location:`.

## Key Insight

An edge redirect layer that matches the full URI exactly inherits none of the
origin's URL normalization. Enumerate every form a client can present — the
origin's current normalization behavior (trailing-slash appends, `index.html`
resolution) is a *masking* dependency, not coverage, and it evaporates the
moment the origin machinery is deleted. The correct enumeration question is
"what can reach the edge", not "what does the stub emit".

Second-order: expanding coverage rippled a count (46 → 69, 58 → 82, 12 → 13)
through ~20 sites across 5 files — the same #7826 instrument-class failure
(the first pass fixed comments where the author had touched and missed the
rest). The sweep that closed it was keyed on the claim's **subject** (every
`46`, `58`, `12`, `2 URL shapes`, `both URL shapes` occurrence repo-wide), not
on the diff's file list, and the residual-zero grep was followed by reading
each surviving hit in context — including the `~460`/`~690` near-miss that a
word-boundary-blind `s/46/69/` would have mangled the wrong way (here it
happened to land correctly, verified by re-read).
