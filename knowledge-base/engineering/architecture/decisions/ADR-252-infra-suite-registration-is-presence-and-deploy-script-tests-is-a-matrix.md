# ADR-252: Infra suite registration is filesystem presence; deploy-script-tests partitions via matrix legs over the parallel runner

## Status

Accepted — 2026-09-24. Delivers #8736; closes the standing dissent it
recorded (shard the job vs keep re-deriving a serial ceiling).

## Context

`infra-validation.yml`'s `deploy-script-tests` job ran ~146
`run: bash <suite>.test.sh` steps serially on a 4-vCPU runner. Measured
2026-09-24: successful main-push runs took 1170–1462 s, and the job's
`timeout-minutes` had been re-derived upward six times in ten weeks
(8 → 12 → 14 → 15 → 20 → 27 → 35) because every landed suite appended
itself serially. The job is the only push-time execution of these suites
(#6766), so its wall clock was the tail latency of every main-push CI
cycle.

Two contracts pinned that shape:

- **Registration was a step shape.** The `suite-command-registration`
  gate (`.github/scripts/test/test-infra-suite-registration.sh`) asserted
  each tracked suite appear as a literal single-line `run: bash <path>`
  step — a PR that consolidated suites into a runner call de-registered
  them. The shape was load-bearing: it produced per-suite named
  attribution in the GitHub UI for free, and the runner scraped those
  lines to derive its execute set.
- **The scrape was lossy.** `run-registered-suites.sh` matched single-line
  `run: bash` only — six subdirectory suites carried correct steps but were
  structurally underivable (#7076), and the three root-requiring loopback
  suites ran via `sudo bash` inside `run: |` blocks the scrape also could
  not see. The derivation was a text match on YAML, not a model of what
  exists.

ADR-238 had already cut `test-scripts` the other way — matrix legs over a
parallel runner with a checked-in duration-aware manifest (ADR-240) — and
its rejected-alternative reasoning ("splitting multiplies fixed cost")
was the objection any infra sharding had to answer *with numbers*.

## Decision

1. **Presence is registration.** A tracked file under
   `apps/web-platform/infra/**.test.sh` IS a registered suite. The runner
   derives its execute set with `git ls-files` — the same set a fresh
   checkout contains — so the derivation cannot disagree with the file
   that a clone would have. The old failure modes die with the scrape:
   subdirectory suites register automatically, and nothing can be "named
   in the workflow but absent from the set".

2. **`deploy-script-tests` is a K=4 matrix, `fail-fast: false`, one
   runner invocation per leg** carrying `SOLEUR_INFRA_SHARD=k/4`. The
   runner executes each leg's subset at `-P min(nproc,6)` — 4-wide on the
   4-vCPU runner it actually gets. Full width is a considered choice, not
   an oversight — but an honest one: #7376 measured `-P4` flakiness on
   exactly this hardware and left the cause *unresolved* (resource
   exhaustion vs shared-state collision was never established). What this
   design changes is not the race but the blast radius: under the old
   serial job a flaky suite was an anonymous red step; under a leg it is
   a bounded, named RED with a retained log — attributable in one click
   rather than six executions. If #7376's mechanism resurfaces, it lands
   on one leg with the suite named. `main-health-monitor` keeps `JOBS:1`
   because its failure mode is a spurious P1 page, which is worse than a
   slow leg here.

3. **Attribution moved from step count to verdict lines + artifacts.**
   Per-suite `PASS`/`RED` lines and `::error` annotations name the suite;
   per-suite stdout/stderr logs upload as a leg artifact on failure;
   per-suite `.trow` timings upload always and feed the manifest
   generator. The registration gate asserts the *connection* (runner
   step present, shard-wired, unmasked, fail-open-proofed) rather than a
   step per suite.

4. **Leg assignment is checked-in derived data, per ADR-240.**
   `apps/web-platform/infra/suite-shard-legs.tsv` is generated by
   `scripts/regenerate-shard-manifest.py --group infra` from uploaded
   `suite-timings-infra-*` artifacts — sticky-LPT, seeded from the
   measured per-step table so the first sharded run is already balanced
   (369–370 s/leg). Untabled labels hash-fallback; a stale manifest is a
   balance problem, never a coverage one.

5. **The privileged set is explicit, reasoned, and still executed.** The
   three sudo loopback suites are listed in the runner's `PRIVILEGED_WHY`
   map (each entry citing its issue) — derived-but-not-executed under the
   unprivileged runner — and invoked as `sudo bash` steps inside a new
   `deploy-script-tests-fixed` job alongside the other non-glob steps
   (terraform validates, test/infra alert guards, the provenance guard).
   An exclusion waives the runner, never the invocation; the gate enforces
   both halves.

6. **`deploy-script-tests-done` is the single downstream verdict.** An
   `if: always()` aggregator (the ci.yml `test` shape) reads both legs'
   `result`, discriminates a timed-out leg from a superseded run from the
   three result strings it already holds (#7931's discriminator, #8735's
   gap), and is what `notify-main-failure` reads.

7. **Ceilings are per-leg and measured.** `timeout-minutes: 15` on each
   leg is ~2.2× the measured worst leg (~6.7 min incl. ~60 s fixed cost);
   per-suite stalls are bounded inside the leg by the runner's `timeout`
   wrapper (default 360 s, overrides in the runner's bound map for the
   seven suites that carried step-level `timeout-minutes`).

## Consequences

- A suite landing under `apps/web-platform/infra/` requires no workflow
  edit and no ceiling re-derivation — the structure absorbs growth; that
  is the point of the change (#8736's "sustainably" clause).
- Expected wall clock: ~7–8 min per leg end-to-end vs 20–24 min serial,
  with the aggregate verdict at `deploy-script-tests-done`.
- Per-leg fixed cost measured ~60 s (checkout + terraform + cloud-init +
  nftables + docker assert) — K=4 pays ~4 min of duplicated setup to cut
  the tail by ~14 min; K=2 would leave the worst leg at ~12.6 min; K=8
  buys ~90 s for +3 min of fixed cost. ADR-238's "splits multiply fixed
  cost" objection is measured, not assumed away.
- The old step-shape contract is retired: nothing may rely on
  `run: bash <suite>.test.sh` appearing in the workflow. The gate, the
  the self-registration assertions inside twelve suites, and the `work` skill's
  onboarding guidance were all updated in the same change.

## Alternatives considered

| Approach | Verdict | Why |
|---|---|---|
| Affected-only selection on PR runs | Deferred | No per-suite edge index exists for infra suites; once a leg runs ~7 min the marginal win is small. The workflow's `paths:` filter already scopes at PR level. |
| Keep 143 steps; skip per-step via a BASH_ENV shard filter | Rejected | Masking-adjacent: every leg shows ~143 green steps where ~108 did nothing, and the filter is an invisible side-channel on every bash call. Nested `bash <sibling>.test.sh` oracles (≥19 suites) make an outer-only rule delicate. |
| N sibling jobs with explicit per-suite steps | Rejected | Balance decays to author placement; N× duplicated boilerplate; the registration toil that generated this issue persists. |
| Single job, one runner call (K=1) | Rollback shape | ~10.5–12 min projected — misses the target with no margin. The matrix header documents it as the rollback. |
| Prebuilt fixture image / registry cache for the docker legs | Rejected | #7535 D1 measured ~10 s/run benefit against a trust anchor + fork-PR breakage + a prd credential. #8744's apt retry+diagnose landed instead. |
