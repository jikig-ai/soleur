# ADR-084: Decision-classification taxonomy (Mechanical/Taste/User-Challenge) governing autonomous question surfacing

- **Status:** Accepted
- **Date:** 2026-07-04
- **Issue:** #5984 (Wave 1 of the gstack-capability-adoption epic #5983)
- **Relationship to ADR-083:** **consumes** ADR-083's scoped `fable`→`opus` consult as one of two signals at the two gates where it already fires (`plan` Step 4.5, `ship` Phase 5.5). It does not extend the consult mechanism. For the "one-shot inherits, not edited" rationale it **references** ADR-083 §Decision-2/§Alternatives ("Edit one-shot too → Rejected", CONTINUATION-GATE) rather than re-deciding it.
- **Relationship to ADR-053:** stays inside the all-Claude model policy — "both signals" is the session Claude model + the ADR-053-compliant `fable`/`opus` consult. No external vendor.

## Context

gstack `autoplan` classifies every intermediate decision Mechanical / Taste /
User-Challenge and auto-answers all but User-Challenge, surfacing the rest at a
final interactive gate. Soleur wants the same decision discipline but has two
hard constraints gstack does not: (1) the operator is **non-technical** — unilateral
pauses for technical-only findings are friction (`2026-05-25-solo-operator-signoff-gate-defaults-to-noop.md`);
(2) mid-pipeline pauses are an anti-pattern (`2026-05-12-mid-plan-pause-gates-and-operator-step-pushback.md`),
and the autonomous `one-shot`/`work` path has **no operator to ask** (Task
subagents are text-only). A naive port would either bug the operator with
questions they can't answer or hang the pipeline on `AskUserQuestion`.

## Decision

1. **A committed reference doc** — `plugins/soleur/skills/brainstorm-techniques/references/decision-principles.md` — defines the taxonomy, 2 surfacing principles (blast-radius, bias-to-action), classify-by-consequence with 4 never-Mechanical classes, the CTO-fork precedence carve-out, the mode-branch table, the 5-line frame, the consult scope, and the security exception. Consumed by **5 skills**: `brainstorm-techniques`, `plan` Step 4.5, `work`, `ship`, and `plan-review` (#5985 — plan-review classifies its consolidated *review findings* with the taxonomy so named-panel taste findings are surfaced, never auto-applied; a finding-classification use adjacent to the skills that classify their own intermediate decisions).
2. **Classify by consequence, not surface-flavor.** Surface criterion = user-visible OR money/compliance (sub-processor / recurring cost / data egress / lawful-basis). Four classes are never Mechanical even when they look technical: dropping operator-requested scope; a new sub-processor/paid dependency; a new recurring cost; irreversible data ops.
3. **Mode = execution context, not skill name.** Operator-attached ⟺ a real TTY (direct brainstorm/plan, no `HEADLESS_MODE`, not a plan-file arg, not inside a Task subagent). Any subagent / one-shot context is headless — a subagent returns the decision to its parent as structured text.
4. **No-mid-pipeline-pause invariant**, with **one** sanctioned exception: a security/feasibility regression halts **terminally** before merge (a stop, not a per-phase pause) + an `action-required`+`security` issue.
5. **Headless record → `ship`, not `work`.** `work`/`plan` detect and persist challenges to `knowledge-base/project/specs/<branch>/decision-challenges.md`; `ship` Phase 6 renders it into the canonical PR body (under a heading outside the operator-step-gate deny set) AND opens an idempotent `action-required` issue — the surface `operator-digest` Section 4 actually harvests. `ship` is the sole PR-body author and full-replaces the body, so the render must live there (`work` cannot author the body).
6. **one-shot inherits, not edited** — via plan/work/ship, mirroring ADR-083.

## Consequences

- Autonomous runs get principled surface-vs-auto decisions with an operator-legible async surface, and never hang or pause mid-pipeline.
- A new SKILL.md-prose surface across 5 skills; drift-guarded by a `components.test.ts` assertion (doc exists + all consumers link it + `ship` emits the `action-required` issue).
- The doc home (`brainstorm-techniques/references/`) is semantically inverted (the load-bearing consumers are `work`/`ship`), accepted because cross-skill reference-by-path is an established pattern (`deepen-plan` reads `plan/references/*`, `ux-audit` reads `ship/references/*`) and the drift-guard mitigates the rename-orphan risk.
- Fully reversible: delete the doc + the 5 pointers + the ADR.

## Alternatives considered

| Alternative | Rejected because |
|---|---|
| Record the headless challenge in `work` | `work` does not author the PR body; `ship` is sole author and **full-replaces** it — the block would be clobbered. |
| Amend ADR-083 instead of a new ADR | This is a distinct cross-cutting invariant (question surfacing), orthogonal to ADR-083's token-frugal model tiering; amending muddies an Accepted record. |
| Mode-branch keyed on skill name | `plan` runs headless under one-shot (in a subagent) → an interactive branch would hang on `AskUserQuestion`. |
| Mid-pipeline pause on User-Challenge | Anti-pattern (`2026-05-12-mid-plan-pause`); the operator is a solo non-technical founder. |
| Surface all "taste" decisions (gstack's rule) | Technical-taste questions are friction the non-technical operator can't evaluate. |

## Addendum — 2026-10-11 (#10055): consequence class is not authority class

A technical ruling reached the founder twice (the emptiness-evidence threshold, filed as an `action-required` issue on 2026-10-06, and an ADR status flip raised on 2026-10-11), through the pipeline this ADR defines: `plan` persisted it to `decision-challenges.md`, `ship` Phase 6 rendered it and filed an `action-required` issue "Decide how strict …". Decisions 2 and 5 above answer "may the session model auto-decide this?" and "where does an operator-legible record go?"; they were silently reused as "who rules this?". This addendum narrows them. The original text above stays as the dated record.

Ruled by CTO agent, 2026-10-11: amend this ADR rather than mint a new one; the rule `hr-technical-fork-is-not-an-operator-question` is amended in place; the chat-prose Stop-hook arm is not built (13-of-15 over-block record in `unkept-promise-hook.sh`) [Superseded for a cue-based arm, 2026-10-12 (#10057): see the 2026-10-12 addendum below]; the plugin port of the pre-ask gate is deferred (subagents cannot call AskUserQuestion).

- **Decision 1 (precedence carve-out), generalised.** The CTO-fork carve-out covers every technical ruling (architecture fork, threshold or evidence bar, design A-vs-B, whether evidence suffices, a status flip), and legal posture goes to the CLO, in both modes. A technical ruling is never a User-Challenge and is never persisted as an owner item.
- **Decision 2, scoped.** The four NEVER-Mechanical classes decide whether the session model may **auto-decide**; they never decide **who rules**. The operator-only list is closed: money, scope, priority/schedule, irreversible or production-mutating authorization, legal-risk acceptance, brand. The burden of proof sits on "operator".
- **Decision 3, extended.** A headless subagent that has the Agent tool spawns the CTO itself; one that does not returns the row as `pending - assumed: <default>` and its parent (one-shot after the plan phase, otherwise `ship` Phase 5.5) obtains the ruling.
- **Decision 5, split by class.** `decision-challenges.md` carries a `## Decision Classes` table (`Item | Class | Ruling`). `ship` renders technical rows in a `### Ruled by CTO agent` sub-block with no issue, and files the `action-required` + `decision-challenge` issue for operator-class rows only. A script-backed gate (`ship/scripts/technical-ruling-gate.sh`) fails an unruled or mislabelled row and any owner-decision label not carried by `(operator: <category>)`; its remedy is bounded (two CTO spawns, then a draft PR and a `domain/engineering` issue, never an operator question).
- **Decision 6, narrowly superseded.** "one-shot inherits, not edited" no longer holds for one rule: one-shot's plan-subagent prompt carries a short inline copy, because a Task subagent reads prompt text only and a link alone is not read, and one-shot runs the gate once after the plan phase (every exit code handled; two failed CTO spawns end in a draft PR and a `domain/engineering` issue, never an operator question). ADR-083's "one-shot is deliberately not edited" is superseded for these two changes only. A wiring test pins the inline copy's key tokens.
- **Class set.** `technical` (CTO rules), `taste` (the user-legible Taste class: auto-decided with a recommendation, rendered under Model Dissents, no ruling cell) and `operator (<category>)` from the closed list. A user-visible preference is `taste`, never an operator category; taste rows render in the PR body only and file no issue (an accepted residual: operator-digest reads issues, so a preference the model auto-decided is recorded where the operator reads the PR). A choice reversible within the diff that sets no durable contract stays Mechanical and gets no row.
- **Consequences.** The drift guard "`ship` emits the `action-required` issue" now means operator-class rows only. The reference lives at `brainstorm-techniques/references/technical-ruling-delegation.md`; `components.test.ts` derives its consumers (every skill naming the CTO agent must link it). The gate checks form, never truth: a model that mislabels a decision can still write a plausible `operator (scope)` row, which review and the CODEOWNERS-reviewed rule body are the check on.
- **Alternatives considered.** (1) Route every consequence-heavy decision to the operator: rejected, it is the status quo that produced the failure. (2) A Stop-hook label matcher over closing chat text: rejected on the 13-of-15 over-block record and because the gate removes the label at its source. [Reconsidered 2026-10-12 (#10057): that rejection holds for a LABEL arm; a cue-based arm was built, see the 2026-10-12 addendum below.] (3) A hook-only fix: rejected, the carrier was an artifact pipeline, not a tool call, and the hook is repo-local.

## Addendum — 2026-10-12 (#10057): the closing message is a carrier, and a cue arm reads it

On 2026-10-12 the carrier of a technical fork was neither a tool call nor a rendered artifact: it was interrogative sentences in the closing message of a turn ("Decision for you: 1. 2. 3.", "Your calls: is the personal CLI token acceptable? do you want a migration design? rotate Hetzner/R2?"). The rule `hr-technical-fork-is-not-an-operator-question` was in force and its three enforcers (the pre-ask hook, ship's Technical-Ruling Gate, one-shot's single post-plan gate) each read a different carrier. The founder corrected it: "you should ask the CTO, not me ... improve the workflow and skills so we ask those to the CTO in the future".

Ruled by CTO agent, 2026-10-12: build a cue-based Stop hook, repo-local, over the closing message; share its vocabulary with the pre-ask hook through one lib; the earlier rejection of a Stop arm holds for a LABEL arm (no producer once the ship gate removed the label) and is superseded for a cue arm. The 13-of-15 record is a measurement from `unkept-promise-hook.sh` of an over-wide decision/approval VOCABULARY blocking 13 of 15 rule-mandated operator gates; it is why every cue here sits on a `?` sentence behind a business veto and a permission exemption and why the ship bar is zero operator-class hits in a sample of real closings.

- **Mechanism.** `.claude/hooks/pre-closing-technical-fork-gate.sh` (a `Stop` entry in `.claude/settings.json`, ledger row `already-fires` in `devin-dispositions.tsv`) judges each `?`-terminated sentence of the last 1500 bytes of fence-, span- and quote-stripped prose alone, with `tfc_is_fork <unit> shared+closing` from `.claude/hooks/lib/technical-fork-cues.sh`, and blocks at most once per turn (`stop_hook_active`). The pre-ask hook calls the same function with group `shared`, so its behaviour is unchanged while the lib is present; a missing, empty or truncated lib is the one intentional delta (its ruling arm is skipped with a stderr line and its other arms keep running). *(Superseded 2026-10-14: the pre-ask hook now asks for group `shared+ask`; see the 2026-10-14 addendum. `shared` itself is unchanged.)* The cue definitions have exactly one site (the lib); a suite row derives it from the tree.
- **The vocabulary had to grow, not only be shared.** Measured: the existing cues match none of the three questions of the incident, and the operator-vocabulary veto silenced one of them (`deploy` inside `deploy-channel`). The closing group adds CL1 sufficiency, CL2 design (two shapes) and CL3 ordering, vetoed by the BUSINESS words only (`RULING_OPVOCAB_RE` is now their concatenation with the ACTION words, pinned byte-for-byte) plus a closing-only seed list tuned by the sample.
- **Fail open, once, and honest about its reach.** Every parse doubt exits 0 with one stderr line (ADR-157 "What this supersedes": absorbing a failure is correct for a Stop hook, which cannot ask). A permission shape in the same sentence passes: the shared vocabulary (`may i`, `is it fine to`, `ok to`, `go-ahead`, `approve`, `authorize`, `ack-destroy`) plus a closing-only set that binds `can/shall i` and `should i go ahead and` to an action verb. A neighbouring question is judged on its own sentence, so an appended `Approve?` does not exempt a sufficiency question above it. The hook is ONE forced reconsideration per turn, not a guarantee: a repeat after the block runs with `stop_hook_active == true` and passes. It is mostly inert inside a ralph loop (`plugins/soleur/hooks/stop-hook.sh` blocks every Stop and never reads `stop_hook_active`): only the FIRST Stop of a chain is judged (ralph and this hook may both block it, and the model then sees two reasons), every later one, including the one-shot Step 8 closing, carries `true`, so the one-shot pointer line is signage there. The type-asserted, model-controlled input and the absence of `eval` follow ADR-156; the repo reaching toward a plugin follows ADR-178; the lib is a move-never-copy asset (ADR-245).
- **Escapes.** `<stop>OPERATOR-GATE|BLOCKED: ...</stop>` anywhere in the window, a final-sentence `Paused:`/`Blocked:` label (shared with `unkept-promise-hook.sh`, so one appended label disarms both gates), and `Operator-only (category): ...`, which governs only its own sentence and the next unit in its paragraph. The block reason teaches the plain forms and carries no angle-bracket text. This addendum records the stricter-than-ruled scope of the third form as a taste call (S2 in `decision-challenges.md`).
- **Decision 6, once more.** "one-shot inherits, not edited" now also yields to a signage-only pointer line before the Step 8 closing; `go`, `plan` and `work` carry one pointer each, and `work` stays byte-neutral by relocating its explanatory no-marker tail to a reference.
- **Post-implementation rulings (the design-validity pass of the review).** Ruled by CTO agent, 2026-10-12: (Q1) the 600-byte per-unit cap is CUT: the 1500-byte window already bounds a unit, the regexes are linear, and a cap makes any long run-on question an unjudged bypass; a worst-case 1500-byte unit is pinned under a time bound instead. (Q2) the `Operator-only (category):` scoping stays: it keeps recall on an honestly mixed closing like the incident's numbered list; `Paused:`/`Blocked:` remains a documented whole-closing leak shared with `unkept-promise-hook.sh`. (Q3) the `GITHUB_ACTIONS=true` early exit stays (headless CI has no operator, so every block there is wrongful by the rule's premise); it was not in the plan-time rulings T1-T8 and was added after implementation. (Q4) a closing-only permission regex binds `can/shall i` and `should i go ahead and` to an action verb (never bare `should i`, `go ahead`, `proceed` or any `we` form, which are technical-fork shapes); a neighbouring `Approve?` unit does not exempt (the sufficiency ask is the motivating miss). (Q5) `tfc_self_check` is a completion sentinel (the last statement of the lib) plus `declare -f`, not a per-variable list that a new cue would silently miss; the group argument stays a string (a typo is a loud exit 2, a boolean would silently make the hook inert).
- **Telemetry.** The hook's bare `rule_id` is hook telemetry under ADR-205, and the ledger row stores the cue name, the unit length and a sha256, never the text (the CL3 vocabulary is secret-adjacent). The 30-day review counts rows by hook name.
- **Cue-growth tripwire.** More than 6 CLOSING cue patterns (3 today), or 3 founder-reported misses in 30 days, or incidents showing misses inside ralph loops, means the phrase-shaped design has outgrown its budget: revisit judging "Decision for you:" lists that carry no `?`, or stop adding cues. Measured recall on the first sample was about 20% (1 of about 5 technical-fork closings), accepted under the ruling's recall-decay clause; the remedy is the miss, cue, fixture loop, never preemptive widening.
- **Graduation to the plugin** (tracked as #10056, together with the pre-ask gate, after 30 days in service, at least 10 recorded firings, zero founder-reported wrongful blocks and a clean sample re-run): (1) move the lib to `plugins/soleur/hooks/lib/` and have BOTH hooks reach into it, a move never a copy, changing one `TFC_LIB` line per consumer; (2) rewrite only `_tfc_record` for the plugin form; (3) delete the repo-local `settings.json` Stop entry and move the ledger row from `claude-settings` to `soleur-plugin` in the same PR (parity keys on event plus path, so a leftover entry and a new plugin entry would both dispatch unflagged); (4) add a `SOLEUR_DISABLE_*` opt-out to `AGENT_ENV_OVERRIDES` in `apps/web-platform/server/agent-env.ts` and satisfy `plugin-stop-hooks-web-parity.test.ts`; (5) decide `stop_hook_active` absent as fail-open (this hook) versus `// false` (the plugin hook) for Devin and Codex users; (6) decide whether the plain `Operator-only` and `Paused:` vocabulary survives; (7) confirm the cue regexes carry no repo-specific nouns (a suite row asserts it).
- **Alternatives considered.** (1) The plugin placement now: rejected, it runs in web unless opted out and needs the web-parity change, and third-party vocabularies raise the false-positive risk before any in-repo record exists. (2) The exact-label arm of #10057 as written: rejected, brittle once the ship gate removed the label at its source; #10057 is closed by this PR's merge as superseded. (3) One flat cue list that also widens the pre-ask hook: rejected, it widens the AskUserQuestion deny surface and the refactor's regression risk. *(Superseded 2026-10-14 for ONE cue: the `ask` cue widens the pre-ask deny surface through its own group `shared+ask`, with a measured wrong-deny list and a stated residual; see the 2026-10-14 addendum. The flat shared list stays rejected.)* (4) Judging "Decision for you:" lists with no `?`: rejected for now, over-block risk. (5) A whole-closing exemption for any permission ask: rejected, an appended "Approve?" would hide a ruling in the same message.

## Addendum — 2026-10-14 (PR #10286): a brief's own wording is the fourth carrier, and the `ask` cue

The rule `hr-technical-fork-is-not-an-operator-question` was in force when a resume brief said "ask the operator once, then act" about whether leftover roadmap items run as a new pipeline or are recorded as not fixed; the question reached the operator, who said "ask the CTO not me". The carrier was the brief's wording, which no hook can read.

Ruled by CTO agent, 2026-10-14:

- **Skill text carries the brief carrier.** A brief's "ask the operator" / "OPEN DECISION" wording on a technical fork is itself the trigger to spawn the CTO (legal: CLO); the delegation reference classifies the routing of an already-identified gap the brief named as technical (assigning work to a named person stays the operator's). The closed operator-only list keeps its eight category names; only the `scope` definition is clarified.
- **One new cue, in a new group.** `tfc_is_fork <unit> shared+ask`, called by the pre-ask hook only, adds the `ask` cue: a route phrase ("as a new pipeline") AND a record phrase ("as not fixed") in the SAME `?` segment (checked per segment), inside the weak-cue block, so the operator-vocabulary veto and the permission exemption apply. `shared` and `shared+closing` are byte-for-byte unchanged and the Stop carrier cannot reach it (pinned by committed mutants).
- **Cut by plan review.** An ownership-only arm (a measured false deny of "Who should own the remaining items, Alice or Bob?") and a money conjunct (the operator-vocabulary veto already holds the money words).
- **Review rulings (post-implementation, Ruled by CTO agent, 2026-10-14).** The check runs per `?` segment, not over the concatenation of all of them. An ask-only veto (`drop|defer|scope`) leaves a genuine scope ask to the operator, and ROUTE is pipeline-shaped only (`pipeline|one-shot`), so a triage ask about an issue or PR is not a routing call. A lib that predates the group is announced on stderr and the hook falls back to group `shared`; the incident message carries the cue name. No production hook asks for plain `shared` first; the pre-ask hook's version-skew fallback does, so it stays.
- **Residual, stated.** Ownership-only and scope-limited phrasings, a split across two sentences, halves only in option labels (no cue reads them), a permission-shaped question (the permission exemption applies to every cue), and a sentence that names drop, defer or scope stay allowed; the skill text covers them. The Stop carrier is excluded on purpose: the cue was never measured against closing messages.
- **Budget for the family.** The cue-growth tripwire above counts CLOSING cues only. For `ask`: more than 3 `TFC_ASK_*` patterns, or a second paraphrase miss, means stop widening and revisit.
