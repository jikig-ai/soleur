# ADR-314: launch-check — a skill whose analysis is read-only, whose Soleur baseline is derived from the guard manifest and whose issue filing is opt-in (amended 2026-11-03)

## Context

Customers who arrive with an existing repository and an MVP (the first is alpha tester #1) have no way to learn what stands between that repo and real users, nor which Soleur engineering practices it lacks. `/soleur:sync` bootstraps a knowledge base but is a write path that the web platform runs headless on every clone (`apps/web-platform/server/auto-sync-trigger.ts`), and its customer-repo path had defects (#7442, fixed; #7452, post-MVP follow-ups still open). `soleur:verification-scaffold` installs four guards but cannot say which are missing.

## Decision

1. **A new skill, `launch-check`, not a `/soleur:sync` area and not a `verification-scaffold` mode.** It is model-invocable (its 18-word description is counted in the skill-description budget, which has only a few words of headroom left) because a customer asking whether their repository is ready should reach it; its analysis writes exactly one file, `knowledge-base/engineering/readiness/launch-check.md`.
2. **The Soleur-baseline guard checks are derived at run time from `verification-scaffold/references/guards.tsv`** (`tier=v1` rows, columns resolved by header name). They are never listed in the skill (ADR-193, "the population is derived, never listed"). An empty or unreadable manifest aborts with `reason=baseline-source-empty`; it never reads as "zero baseline checks". Non-guard conventions (agent-conventions file, architecture notes, the Next.js import-boundary gate) are rows in `references/checks.tsv`.
3. **Findings carry the check id as their identity.** Re-runs diff against the previous report's fenced state block (`schema_version`, `catalog_hash`, one `finding <id> open|accepted [date reason]` line per finding), listing closed, new, accepted and retired ids. A customer accepts a finding by editing its state line. No issue numbers live in the state block.
4. **Packaging constraint.** Everything the skill reads at run time ships inside `plugins/soleur/`. The plugin root is resolved by identity (the manifest names `soleur`), and a missing `guards.tsv` or `redact-sentinel.sh` aborts with `reason=plugin-root-unresolved` (#7442).
5. **Redaction trust boundary.** One chokepoint, `lc_emit_checked`, scans the exact report bytes with `redact-sentinel.sh` and `gitleaks` and writes nothing on a hit or on a scanner that did not run. Secret-class findings (`SEC-01`, `SEC-02`) are counts only; their locations never reach any file. The AI-assisted review items use a closed schema (status, severity enum, evidence ids), so free text from that step cannot pass the scanner; titles and remedies come from the catalog. The facts file is not trusted either: `render` validates it against the catalog (every non-judged id exactly once, known statuses) and passes evidence only if it is a fixed detector phrase, a bare path or `path:line` (count-only ids keep fixed phrases), and it parses the previous report with the state-line grammar, refusing a report that has no state block. A check that did not run (`na`, `unsupported-stack`, an unreviewed AI-assisted item) is carried or listed under *Not assessed*, never closed. All report prose originates in static files under `references/`, linted for assurance wording by a test.
6. **Local CLI, no telemetry** (amended 2026-11-03, see Amendment). The skill runs on the customer's machine and key and has no network call and no share-back path. A hosted variant is out of scope until an Art. 28(3) instrument exists. The skill is model-invocable and ships inside the plugin, so nothing in the plugin stops a hosted agent from loading it: the platform must not enable it until that instrument exists. Unattended runs (`CI`, or `LAUNCH_CHECK_HEADLESS=1`) are refused a report write by the script. The scanner, sentinel and manifest overrides (`LAUNCH_CHECK_GITLEAKS`, `LAUNCH_CHECK_REDACT_SENTINEL`, `LAUNCH_CHECK_GUARDS_TSV`) are honoured only under `LAUNCH_CHECK_TEST=1`, so an inherited environment variable cannot weaken the redaction gate. `scan --show-secrets` needs a real terminal.
   SEC-01 scans every file of the last commit through a throwaway index (not `git archive`, which honours `export-ignore`), including the never-read classes, ignoring the repository's own gitleaks configuration; a snapshot that cannot be read aborts instead of reading as clean.
7. **Issue-epic creation** (built; see Amendment). Every `gh` write goes through one function that executes only a saved preview plan, refuses under `--dry-run` and headless, and treats an existing marked issue (open or closed) as present. Consent is skill-enforced (the customer is asked before `--create`) plus the harness permission prompt; the script cannot prove human approval.

## Alternatives Considered

| Alternative | Why rejected |
|---|---|
| A `/soleur:sync` area | `sync` is a write path run headless on every clone; an unattended analysis plus issue creation there would act on every connected repo with no approval step, and its customer-repo path is already broken in places. |
| `verification-scaffold --audit` | The manifest has four v1 guards; it cannot express production readiness (observability, scale, architecture). The baseline reuses the manifest instead. |
| A hand-listed baseline inventory | Goes stale on the next manifest edit; contradicts ADR-193. |
| A readiness score | Reads as an attestation (CLO, CMO); the report is a findings list with a standing banner. |
| Fingerprint- or path-keyed finding ids | Would put a secret's location or a renamed path into committed state; check ids are stable and carry no location. |
| `gh issue create` / `gh label create` for the issue writes (amendment 2026-11-03) | Two reasons, neither of them a hook: the flags and `--json` field set of `gh issue ...` differ across the `gh` versions a customer may run (version skew), and one allowlisted executor is easier to pin than several verbs. (The guardrails filing gate reads only the top-level Bash command text, so it never sees a write made inside a script and is not a reason for either choice.) Every read and write goes through `gh api` (REST), which exists on every version, returns `.id` and `.number` from the create call in one request, and keeps the write shapes to a small allowlist. |

## Consequences

- Adding a v1 guard to `guards.tsv` adds a baseline check with no code change; the `baseline.test.sh` suite pins that by name identity.
- The baseline is small (four guards plus three conventions); a repository that has the original form of a guard (the source repo itself) is recognised through the manifest's `source_files` column.
- Detectors are heuristics. A negative reads "not identified in the files read", and the banner states that absence of findings is not assurance.
- Scan time scales with repository size (about 27 s on this 20k-file monorepo, dominated by gitleaks).

## Amendment — 2026-11-03 (#11910, PR-B: severity-ranked epic with sub-issues)

Status stays `adopting` until the first real customer run. This amendment amends decisions 6 and 7; the parts of decision 6 it does not restate stand (the local CLI on the customer's machine and key, no telemetry, no share-back path, no hosted variant until an executed Art. 28(3) instrument exists and the platform must not enable it before then, the test-only seams, and `scan --show-secrets` needing a real terminal). The rest of the ADR stands.

**Decision 6, as amended.** The analysis (`scan`, `render`, `verify-report`) has no network call and writes only the report. One command is the exception, `launch-check.sh issues`, with the customer's own `gh` login, on github.com (another host only with an explicit `--host`): `--preview` makes read-only authenticated GETs to the customer's **own** repository (the repository's metadata, the labelled issue listing and the signed-in login) and writes a plan directory (mode 700, under `TMPDIR` or `--plan-out`) holding what it would send; `--create` is the only writer to the tracker, confirm-gated, from that saved plan. Soleur operates no server in that path, receives nothing and stores nothing, so the Art. 28(3) posture is unchanged: this is the supplier's tool running on the customer's machine and key, and a hosted variant stays out of scope and dark until an executed instrument exists. Unattended runs (`CI` non-empty, or `LAUNCH_CHECK_HEADLESS` set to `1`, `true` or `yes`, any case) may preview but never create: the refusal is enforced at argument parse and again inside the one write wrapper. The `plugin -> github` edge for these calls is in `model.c4`, separate from the opt-in release-lookup edge because the data owner and the direction differ.

**Decision 7, as built.** The four guards the suites pin by number:

- **Guard 1, saved-plan-only writes.** `--preview` writes a plan directory (mode 700: `plan.tsv`, `epic.md`, `issues/<ID>.md`); `--create` accepts nothing else. It checks owner, mode and symlinks with `lstat`, copies the plan into its own scratch directory, validates every `plan.tsv` field against a closed vocabulary, regenerates every title and body from the catalog, facts and ids, and byte-compares them with the plan. Any difference aborts `plan-invalid`. Every `gh` write passes through one function that refuses headless and `--dry-run` and accepts exactly four REST shapes (label create, issue create, sub-issue link, issue-body edit on the epic), a fixed set of field keys (an edit can never carry `state`), label names that start `lc:`, a PATCH or link only under the epic this run found or created, and `@file` operands only inside the validated plan. Reads always carry `-X GET`; `auth` and `repo` reads are limited to `status` and `view`, and every read refuses a flag outside the shapes the callers use (such as `--show-token`, `--web`, `--input`, `-H` or `--hostname`). `gh` runs with `GH_HOST` forced to the target host and a scrubbed environment (the variable list lives in `lc__gh_exec` and is pinned by the environment row of `test/issues-guards.test.sh`), with stdin from `/dev/null`. Raw `gh` stderr and tracker text are never printed: `detail=` is a closed token set.
- **Guard 2, authored bytes are scanned bytes.** Every byte this tool authors into a tracker (titles, bodies, label names and descriptions, the epic section) is the plan copy, scanned through `lc_emit_checked` in scan-only mode, run from the gate's scratch directory so a customer `.gitleaksignore` is never read, before the first write; the preview scans what it is about to show the same way. Text the customer writes elsewhere in the tracker is not authored by this tool. Secret-class findings are counts only.
- **Guard 3, idempotency and resume.** The identity is the scope label `lc:launch-check` plus a body marker `<!-- launch-check:gap=<ID> -->`, found by one paginated REST listing; a marker counts only as a whole line, trailing spaces, tabs and a CR tolerated (a note that quotes one mid-text, or an indented or block-quoted one, is not a marker). Open or closed counts as filed. A listing that fails aborts `issues-incomplete phase=lookup` rather than reading as empty. A marked issue missing from the epic's live `sub_issues` is re-linked, not recreated. The first failed write stops the run; re-running is the retry (no backoff ladder).
- **Guard 4, epic edits confined to the marked section.** Only the text between the epic's begin and end markers is ever rewritten, from a fresh GET just before the edit.
- **Consent.** `--confirm-repo` and `--confirm-count` must equal the plan's repository and create count; they are a transcription guard, not proof of human intent. `--confirm-public` is required when the LIVE visibility is public, internal or unknown. The skill must ask the customer, naming the repository, visibility, fork status, count and labels, before `--create`; the script cannot prove human approval, and the harness permission prompt is the second control. The tool never closes, relabels or deletes an issue.
- **Markers are unmirrored.** `SOLEUR_LAUNCH_CHECK_ISSUES`, `SOLEUR_LAUNCH_CHECK_ISSUES_PLAN` and `SOLEUR_LAUNCH_CHECK_PLAN_OK` are emitted from `scripts/lib/issues.sh`, outside the telemetry drift guard's `skills/*/scripts/*.sh` walk (the same precedent as `_ABORT`), and deliberately have no telemetry mirror: they carry the customer's repository slug and the only sink is the customer's own tool result. A comment in `apps/web-platform/server/git-lock-marker-telemetry.ts` records this next to the existing launch-check note, and a test pins that the extractor stays blind to them. A hosted run is a non-goal and dark.
- **Accepted risks.** No create-time lock (two concurrent runs can both pass the re-list; only a second epic is caught); the live sub-issue endpoint is checked against a stub only in this change, with the live check tracked in #11956.

**Deviations from the plan this was built from, and the review-round rulings.**

- **No TTY test.** The parent plan had `gh_write` refuse any no-TTY invocation. A TTY gate adds nothing here: an agent's Bash tool has no TTY, so the check could not tell an attended agent session from an unattended one. Headless is `CI` non-empty or `LAUNCH_CHECK_HEADLESS` set to `1`, `true` or `yes`; the consent control is the question the skill asks before `--create`.
- **Epic title.** The parent plan titled the epic `Launch readiness: <repo> (launch-check)`; the epic is titled with the fixed phrase `Launch-check gaps` (from `references/phrases.txt`), which carries no repository name.
- **L1, link failures.** Only a refusal of the feature itself (HTTP 403, 404, 410 or 422) latches the whole run to the task list in the epic. A rate limit, a transport failure or timeout, or a 5xx stops the run `issues-incomplete phase=link`, and the idempotent re-run links what is still unlinked. The latch is provisional: a later run upgrades a task-list epic to real links when GitHub accepts them.
- **L2, the printed command.** The `--create` command the preview (and the resume hint) prints never contains `--confirm-public`; a separate line says that, only after the repository owner's own separate yes, it may be appended. A command copied and run whole must not publish a list of unfixed gaps on its own.
- **L3, hosted headless override (refined by L9).** The hosted agent environment (`apps/web-platform/server/agent-env.ts`) sets `LAUNCH_CHECK_HEADLESS=1`, pinned by a test. That is a seatbelt against an ambient or accidental run, not a mechanical gate: a Bash call can set the variable inline, and this change adds no hosted Bash deny. With it set, `--create` is refused and a hosted session may scan, preview and `render --dry-run`; a hosted `render` that writes the report is refused too, with `headless-write-refused`, which is a side effect of the same override. The hosted variant stays dark because the platform does not enable the skill, not because this variable cannot be bypassed.
- **L4, banner and markers.** Every filed sub-issue body and the epic carry the standing banner from `references/banner.txt` as the block after the marker line. Marker identity is read from whole-line markers only. `--create` aborts `epic-ambiguous` for an epic candidate (an issue with the `lc:epic` label that carries several markers or none, or an epic marker among several) and `issue-ambiguous` when an issue with several markers carries the marker of a finding in this plan; any other issue that carries the scope label but no usable marker is ignored and counted and named in the preview.
- **L7, origin host.** The origin hosts `ssh.github.com` and `www.github.com` are read as `github.com`. For any other host that differs from the target (an ssh alias), an explicit `--repo OWNER/NAME` that equals the repository gh resolved bypasses the host-differs abort (the owner named the target and `--confirm-repo` still transcribes it); without `--repo` the run aborts `repo-unresolved detail=host-differs` and the remedy says to pass `--repo` or fix the origin remote, never `--host <alias>`.
- **L8, enterprise tokens.** Both `GH_ENTERPRISE_TOKEN` and `GITHUB_ENTERPRISE_TOKEN` are scrubbed unconditionally in `lc__gh_exec` (fail closed): a GitHub Enterprise Server user relies on the login `gh` stores for the host `--host` names.
- **L9, hosted headless override.** See L3: the override is a seatbelt, not a mechanical gate; no hosted Bash deny is added here.
